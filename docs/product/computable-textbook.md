## 1. 项目目标

### 1.1 背景

传统学习系统通常存在以下问题：

* 教材文档（Markdown / PDF / Word）主要服务于阅读，**可读但不可计算**。
* 知识点关系大多隐含在文本叙述中，**结构不显式**。
* 学习路径难以根据用户掌握情况动态调整，**缺少个性化机制**。
* 出题、评估、讲解与教材内容割裂，**难以形成统一知识闭环**。

因此，需要构建一种新的教材组织方式，使教材不仅是内容载体，同时也是可解析、可推理、可评估、可生成的知识系统。

### 1.2 目标定义

本项目的目标是构建一个：

> **可计算教材（Computable Textbook）系统**

使教材具备以下能力：

| 能力  | 描述                       |
| --- | ------------------------ |
| 可解析 | 将 Markdown 等文档解析为结构化知识单元 |
| 可推理 | 基于知识图谱进行依赖分析、路径推理与关系扩展   |
| 可评估 | 针对用户建立知识掌握度模型            |
| 可生成 | 自动生成题目、讲解内容与学习建议         |
| 可演化 | 根据用户兴趣、学习行为与知识变更动态更新视图   |

### 1.3 一句话定义

> **教材不再只是“给人读的文档”，而是“可执行的知识系统”。**

## 2. 核心设计理念

### 2.1 三层模型

系统围绕三个核心抽象构建：

```text
        用户交互层
   （学习 / 出题 / 评估 / 导航）
              ↑
   ┌────────────────────┐
   │   知识单元层（KU）   │
   └────────────────────┘
      ↑                ↑
Markdown（书）     KG（地图）
```

这三个层次分别承担不同职责，但通过 KU（Knowledge Unit）实现对齐。

### 2.2 Markdown = 书

Markdown 的本质是：

> **线性认知表达**

其特点包括：

* 面向人类阅读
* 支持连续语义表达
* 适合承载推导、例子、图示、说明
* 保留教材的自然叙述结构

Markdown 的职责是“**讲清楚**”。

### 2.3 KG = 地图

知识图谱（Knowledge Graph）的本质是：

> **知识拓扑结构**

其特点包括：

* 将知识点表示为离散节点
* 将知识依赖、推导、应用等关系显式化
* 支持路径推理、关系扩展、子图生成
* 便于出题、推荐、导航与评估

KG 的职责是“**算清楚**”。

### 2.4 KU = 坐标系

KU（Knowledge Unit，知识单元）的本质是：

> **书与地图之间的统一锚点**

KU 既要能够指向 Markdown 中的具体内容位置，也要能够映射到 KG 中的节点与关系，从而完成文本世界与结构世界之间的对齐。

KU 的职责是“**对齐清楚**”。

## 3. KU（知识单元）设计

### 3.1 KU 定义

KU 是系统中的最小可计算知识单元。

定义原则：

> **KU = 可以独立出一道题的最小单位**

这一定义非常关键，因为它直接决定了后续：

* 出题粒度
* 用户掌握度建模粒度
* 学习路径的节点粒度
* 图谱关系的可解释性

### 3.2 KU 粒度示例

| 内容     | 是否适合作为 KU |
| ------ | --------- |
| 一整章内容  | ❌         |
| 一节内容   | 一般不建议     |
| 一个概念定义 | ✅         |
| 一个公式   | ✅         |
| 一个推导步骤 | ✅         |
| 一个例题   | ✅         |
| 一个方法步骤 | ✅         |

### 3.3 KU 类型体系

建议支持以下基础类型：

```text
concept      概念
definition   定义
theorem      定理
formula      公式
example      例题
exercise     习题
method       方法
proof_step   推导步骤
remark       注释/补充说明
```

其中，`proof_step` 和 `remark` 可作为增强类型，在理工科场景中尤其有价值。

### 3.4 KU 标准结构

```json
{
  "id": "ku_linear_regression_definition",
  "type": "concept",
  "title": "线性回归定义",
  "content_ref": {
    "doc_id": "ml_regression.md",
    "anchor": "#ku_linear_regression_definition"
  },
  "relations": [
    {
      "type": "prerequisite",
      "target": "ku_least_squares"
    },
    {
      "type": "derivation_of",
      "target": "ku_normal_equation"
    }
  ],
  "embedding": [],
  "attributes": {
    "difficulty": 0.6,
    "importance": 0.9,
    "cognitive_level": "understand"
  }
}
```

### 3.5 KU 字段说明

| 字段          | 含义                  |
| ----------- | ------------------- |
| id          | KU 的全局唯一标识          |
| type        | KU 类型               |
| title       | KU 展示名称             |
| content_ref | 对应 Markdown 文档与锚点位置 |
| relations   | 与其他 KU 的关系          |
| embedding   | 用于语义召回与兴趣建模         |
| attributes  | 难度、重要度、认知层级等属性      |

### 3.6 KU 设计原则

KU 设计必须遵循以下原则：

1. **原子性**：应尽可能小，但仍保持语义完整。
2. **可题目化**：能够成为独立评估对象。
3. **可锚定**：必须能回指到教材中的具体位置。
4. **可关联**：必须能纳入图谱关系网络。
5. **可演化**：允许后续新增属性、关系和掌握度状态。

## 4. Markdown（书）设计

### 4.1 设计目标

Markdown 是面向学习者的主要阅读载体，因此需要在保持可读性的同时，增加结构化标记，使其可以被程序解析为 KU 与关系。

### 4.2 基础规范：显式锚点

建议在 Markdown 中引入稳定锚点 ID：

```markdown
## 线性回归定义 {#ku_linear_regression_definition}

线性回归是...

---

### 最小二乘法 {#ku_least_squares}

...
```

该锚点用于：

* 构建 `content_ref`
* 支持前端跳转与高亮
* 实现 Markdown 与 KU 的双向定位

### 4.3 语义增强标签

在保持 Markdown 可读性的前提下，可以添加轻量语义标签：

```markdown
## 正规方程 {#ku_normal_equation}

[prerequisite: ku_least_squares]
[related: ku_linear_regression_definition]
[type: formula]

公式如下：

$$
w = (X^TX)^{-1}X^Ty
$$
```

这类标签既可手工维护，也可由系统补全后回写。

### 4.4 Markdown 的职责边界

Markdown 中适合承载的内容：

| 内容       | 是否属于 Markdown |
| -------- | ------------- |
| 概念解释     | ✅             |
| 推导过程     | ✅             |
| 图表与例子    | ✅             |
| 公式与说明    | ✅             |
| 用户掌握度    | ❌             |
| 用户兴趣偏好   | ❌             |
| 动态学习路径结果 | ❌             |
| 图谱全局关系图  | ❌             |

Markdown 应始终聚焦于“内容表达”，不应混入用户态和系统态信息。

### 4.5 Markdown → KU 抽取流程

```text
Markdown 文档
   ↓
AST 解析
   ↓
识别显式锚点 / 标签
   ↓
切分为 KU 候选片段
   ↓
生成 KU 结构
   ↓
抽取显式关系 / 推断隐式关系
   ↓
入库并同步到 KG
```

### 4.6 Markdown 作为事实源

系统推荐采用：

> **Markdown 作为知识内容的主事实源（Source of Truth）**

即：

* 教材内容修改应首先发生在 Markdown 中
* KU 与 KG 由 Markdown 解析和同步生成
* 图谱不直接反向修改教材正文内容

这样可以避免结构层与文本层长期分叉。

## 5. 知识图谱（地图）设计

### 5.1 KG 的定位

知识图谱不是教材的替代品，而是教材的结构化镜像与计算层。

其作用包括：

* 表达知识依赖关系
* 支持路径推理
* 生成用户兴趣子图
* 支持基于图结构的出题与推荐
* 为 RAG 增加结构约束

### 5.2 基本结构

```text
(KU) --prerequisite--> (KU)
(KU) --derivation----> (KU)
(KU) --application---> (KU)
(KU) --example_of----> (KU)
(KU) --similar-------> (KU)
(KU) --contrast------> (KU)
```

### 5.3 核心关系类型

建议最小可用关系集合如下：

| 关系类型         | 含义     |
| ------------ | ------ |
| prerequisite | 前置知识   |
| derivation   | 推导关系   |
| application  | 应用关系   |
| example_of   | 例题归属关系 |
| similar      | 相似概念   |
| contrast     | 对比关系   |
| part_of      | 局部属于整体 |
| next_step    | 学习顺序建议 |

其中，`prerequisite` 与 `derivation` 是第一优先级关系。

### 5.4 KG 节点来源

KG 的节点以 KU 为核心，但后续可扩展出更高层抽象：

* Topic（主题）
* Chapter（章节）
* Knowledge Unit（知识单元）
* Question Template（题目模板）
* User Mastery State（用户掌握状态投影）

MVP 阶段建议只使用 KU 作为主节点类型，降低复杂度。

### 5.5 存储建议

推荐采用混合存储方案：

| 数据类型  | 推荐技术                      |
| ----- | ------------------------- |
| 图结构   | Neo4j / ArangoDB          |
| 向量索引  | FAISS / Milvus / pgvector |
| 业务元数据 | PostgreSQL                |

如果当前项目以 SQLite / PostgreSQL 为主，也可以先在关系数据库中模拟图关系表，实现 MVP。

## 6. 同步机制设计

### 6.1 基本原则

系统的核心同步方向应为：

```text
Markdown → KU → KG
```

即：

* Markdown 是内容事实源
* KU 是标准化中间层
* KG 是可计算结构层

### 6.2 允许的局部回写

虽然正文内容不建议由 KG 直接改写，但允许将部分系统性信息回写到 Markdown 或附属元数据中，例如：

* 推荐难度标记
* 自动生成的关系建议
* 维护性提示
* 缺失前置知识提醒

同时，以下动态信息应保留在系统层，不直接写入正文：

* mastery（掌握度）
* personalized difficulty（个体难度）
* review scheduling（复习计划）
* user focus（用户兴趣向量）

### 6.3 更新流程

```text
编辑 Markdown
   ↓
解析 AST
   ↓
识别 KU 变更
   ↓
计算 diff
   ↓
更新 KU 表
   ↓
更新 KG 节点与边
   ↓
重建或增量更新 embedding
```

### 6.4 变更类型

建议支持以下几类增量更新：

* **内容变更**：正文修改但锚点不变
* **结构变更**：新增 / 删除 / 拆分 / 合并 KU
* **关系变更**：新增 / 删除关系标签
* **锚点变更**：KU ID 或位置发生变化

系统应尽可能支持增量同步，而非每次全量重建。

## 7. 用户建模系统

### 7.1 用户状态目标

用户建模层用于回答两个问题：

1. 用户当前会什么？
2. 用户接下来该学什么？

### 7.2 基础状态结构

```json
{
  "user_id": "u1",
  "mastery": {
    "ku_linear_regression_definition": 0.3,
    "ku_least_squares": 0.7
  },
  "focus_embedding": []
}
```

### 7.3 核心状态字段

| 字段              | 含义            |
| --------------- | ------------- |
| mastery         | 用户对每个 KU 的掌握度 |
| focus_embedding | 用户近期关注方向的语义向量 |
| review_due      | 待复习知识单元       |
| learning_goal   | 当前学习目标        |
| weak_areas      | 薄弱知识点集合       |

### 7.4 掌握度模型建议

MVP 阶段推荐从简单方案开始：

#### 方案 A：指数衰减 + 正确率

优点：

* 实现简单
* 易解释
* 适合原型期快速上线

#### 方案 B：BKT（Bayesian Knowledge Tracing）

适合：

* 离散题目反馈场景
* 有较明确知识点归因

#### 方案 C：IRT（Item Response Theory）

适合：

* 题库较成熟
* 希望对题目难度与用户能力同时建模

推荐路线：

> **先用简单 mastery 评分模型上线，再逐步演化到 BKT / IRT。**

## 8. 学习路径与出题系统

### 8.1 学习路径生成

给定一个目标 KU，系统可通过知识图谱中的前置关系逆向展开，构建学习路径：

```text
目标 KU
   ↓
沿 prerequisite 反向搜索
   ↓
构建依赖子图
   ↓
结合 mastery 裁剪
   ↓
输出个性化学习 DAG
```

路径生成时应考虑：

* 前置知识是否已掌握
* 当前认知负荷是否过高
* 同层知识点是否可并行学习
* 是否存在更短的学习闭环

### 8.2 出题目标

出题系统应服务于以下目标：

* 检测用户掌握度
* 强化薄弱点
* 支撑复习计划
* 帮助完成章节学习闭环

### 8.3 出题策略

#### 策略一：基于薄弱点

```text
mastery < threshold → 优先出题
```

适合查漏补缺。

#### 策略二：基于学习路径

若学习路径为：

```text
A → B → C
```

则可分层生成：

* A：基础识记题
* B：理解或应用题
* C：综合推导题

#### 策略三：基于多跳关系

对于链式关系：

```text
A → B → C
```

可生成多跳题：

> 已知 A，推导或解释 C。

这类题目更适合衡量真正的理解能力，而非局部记忆。

### 8.4 KU 与题目的映射原则

建议题目至少绑定一个主 KU，并可带多个辅 KU：

* 主 KU：本题主要评估对象
* 辅 KU：本题涉及的辅助知识点

这样才能较准确地将题目反馈回流到掌握度模型。

## 9. RAG 升级：从纯向量召回到 KG + RAG

### 9.1 当前问题

纯 embedding 检索常见问题包括：

* 语义相近但知识路径错误
* 缺少必要上下文
* 无法补全前置知识
* 容易召回表面相似但结构不相关的片段

因此，仅依赖 chunk 向量检索并不可靠。

### 9.2 升级思路

引入知识图谱后，推荐采用以下流程：

```text
用户 Query
   ↓
基于 embedding 召回候选 KU
   ↓
基于 KG 进行关系扩展与结构补全
   ↓
回溯到 Markdown 中的原始内容片段
   ↓
构造上下文
   ↓
LLM 生成答案 / 讲解 / 题目
```

### 9.3 优势对比

| 方法       | 主要问题 / 优势     |
| -------- | ------------- |
| 纯向量 RAG  | 召回结果容易语义漂移    |
| KG + RAG | 具备结构约束与路径可解释性 |

### 9.4 典型增强点

KG + RAG 可以增强以下能力：

* 自动补充前置知识
* 自动扩展相邻概念
* 自动构造讲解路径
* 保证回答不脱离教材结构
* 为“为什么先学这个、再学那个”提供解释

## 10. 用户关注子图设计

### 10.1 问题定义

在大型知识图谱中，用户通常不会长期关注整张图，而只关注其中某一部分，例如某一章、某一主题、某一能力方向。

因此系统需要支持：

> **根据用户兴趣和行为动态生成知识子图视图。**

### 10.2 生成流程

```text
用户兴趣 / 查询 / 行为日志
   ↓
生成或更新 focus embedding
   ↓
召回相似 KU
   ↓
按 KG 进行 1~2 hop 扩展
   ↓
构建用户关注子图
```

### 10.3 子图的作用

用户关注子图可用于：

* 个性化首页展示
* 学习导航
* 题目推荐
* 快速生成当前主题讲解
* 过滤与当前目标无关的知识点

### 10.4 优势

该方案具有以下优点：

* 可解释：能清楚展示为什么某个知识点被纳入视图
* 可控：可限制 hop 数与关系类型
* 稳定：不会像纯向量兴趣模型那样飘移过快
* 可更新：关注变化后只需局部重构子图

## 11. 系统整体流程

### 11.1 内容构建流

```text
Markdown 教材
   ↓
解析器（Parser）
   ↓
KU 抽取与标准化
   ↓
关系抽取 / 关系校验
   ↓
知识图谱构建
   ↓
向量索引构建
```

### 11.2 用户学习流

```text
用户进入系统
   ↓
选择目标主题 / 查询问题
   ↓
召回相关 KU
   ↓
读取用户 mastery 与关注子图
   ↓
生成学习路径 / 题目 / 讲解
   ↓
记录答题结果与行为反馈
   ↓
更新 mastery 与 focus
```

### 11.3 统一视角

```text
           Markdown（书）
                 ↓
         KU 抽取与标准化
                 ↓
          知识图谱（地图）
                 ↓
     用户模型（mastery / focus）
             ↓            ↓
         学习路径        出题系统
             ↓            ↓
           RAG + LLM 生成层
```

## 12. 最终形态：可计算教材

### 12.1 定义

可计算教材并不是简单地把教材数字化，而是把教材升级为：

> **可解析、可推理、可评估、可生成、可演化的知识系统。**

### 12.2 最终能力

| 能力   | 依赖机制               |
| ---- | ------------------ |
| 自动出题 | 基于 KG 路径与 KU 粒度    |
| 个性学习 | 基于 mastery 与用户关注子图 |
| 智能讲解 | 基于 KG + RAG 的上下文构造 |
| 知识导航 | 基于图谱结构与局部子图        |
| 复习调度 | 基于掌握度衰减与评估记录       |

### 12.3 理想用户体验

当用户点击某个知识点，例如“线性回归”时，系统能够同时提供：

1. 对应 Markdown 教材内容（书）
2. 它的依赖关系图与相关知识点（地图）
3. 当前个人掌握度与薄弱点标记（认知状态）
4. 推荐学习路径
5. 自动生成的练习题与讲解

这意味着教材、知识结构与学习行为完成了统一。

---

## 13. 工程落地建议

### 13.1 当前基础

若当前系统已经具备：

* chunk 切分
* embedding 构建
* 基础 RAG 查询

则说明已经有了可计算教材系统的底层基础，但尚未建立中间语义层与结构层。

### 13.2 推荐演进路线

#### Phase 1：引入 KU

目标：建立统一知识单元层。

建议事项：

* 为 Markdown 引入稳定锚点 ID
* 建立 KU 数据表
* 实现 Markdown → KU 解析器
* 建立 KU 与 chunk 的映射关系

#### Phase 2：建立 KG

目标：建立显式知识关系。

建议事项：

* 建立 KU 关系表或图数据库节点/边
* 支持 prerequisite / derivation 等核心关系
* 提供基础图查询接口

#### Phase 3：融合 KG + RAG

目标：提升查询、讲解与出题质量。

建议事项：

* 用 KU 替代粗粒度 chunk 作为召回主单位
* 在召回后通过 KG 做关系扩展
* 从 Markdown 中回溯完整上下文

#### Phase 4：加入用户建模

目标：构建个性化学习系统。

建议事项：

* 引入 mastery 表
* 建立答题反馈到 KU 的映射
* 实现路径推荐与薄弱点优先出题

### 13.3 MVP 建议

MVP 阶段应尽量控制复杂度，建议优先落地以下最小闭环：

1. Markdown 显式锚点
2. KU 抽取
3. prerequisite 关系
4. 基于 KU 的检索
5. 基于 mastery 的薄弱点出题

只要这五项打通，系统就已经具备“可计算教材”的基本形态。

## 14. 关键设计原则总结

### 14.1 三句话总结

> **Markdown 负责讲清楚，KG 负责算清楚，KU 负责对齐清楚。**

> **教材是内容视图，图谱是结构视图，用户模型是认知视图。**

> **三者合并后，教材才真正变成“可计算教材”。**

### 14.2 核心判断标准

今后在系统设计中，遇到任何内容或功能，都可以用以下判断：

* 这个东西是给人读的吗？放 Markdown。
* 这个东西是给机器算的吗？放 KG。
* 这个东西是否需要同时连接文本与结构？放 KU。
* 这个东西是否属于用户状态？放用户模型层。

---

## 15. 后续扩展方向

后续可以继续扩展以下模块：

1. **KU 数据库表设计**：关系型数据库与图数据库双结构方案。
2. **Markdown Parser 实现**：支持显式锚点、标签抽取与增量 diff。
3. **KG 构建脚本**：从 KU 自动构建关系网络。
4. **出题算法**：基于路径、薄弱点、多跳关系自动生成题目。
5. **mastery 模型实现**：从简单评分过渡到 BKT / IRT。
6. **可视化前端**：将“书 + 地图 + 坐标系 + 用户状态”统一展示。
7. **版本化知识演化**：支持教材更新、KU 重构、关系修订与历史追踪。

---

## 16. 结论

本设计的核心不是单独做一个 Markdown 系统，也不是单独做一个知识图谱系统，而是构建一个统一的知识操作体系：

* 用 Markdown 保留人类最自然的学习表达方式
* 用 KG 提供结构化推理与计算能力
* 用 KU 作为两者之间的统一对齐坐标
* 用用户模型把“知识系统”与“学习者”真正连接起来

最终，使教材从静态内容载体升级为：

> **可被计算、可被追踪、可被导航、可被评估、可被生成的教材系统。**

也即：

> **Computable Textbook**
