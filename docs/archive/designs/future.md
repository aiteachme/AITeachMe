## 1. 当前基线与未来边界

当前代码已落地的主能力：

- ingest：两阶段解析与材料层沉淀
- digest：统一构建文档/图谱/课程
- interact：SSE 教学对话
- examine：生成、判卷、回写掌握度
- profile：`user.profile_json + subject.profile_json + user_knowledge_state` 三层

本文件中的 P0/P1/P2 代表“在现有架构上继续扩展”，默认遵循：

1. API 保持简单，优先复用现有资源组。
2. 先复用当前数据主对象，不先扩业务表。
3. 新能力优先通过 workflow 与提示策略升级实现。

## 2. 与 OpenMAIC 对照后的可吸收能力

这部分不讨论“是否做成同样的产品”，只回答一个问题：

**OpenMAIC 里有哪些能力，对 AITeachMe 现有五大引擎是真正有帮助的？**

### 2.1 值得吸收的能力

| 能力 | 建议在 AITeachMe 的形态 | 优先级 | 为什么值得做 |
|------|-------------------------|--------|--------------|
| **构建预览 + 可编辑大纲** | 在 Digest 正式发布前，先给用户看学习路径、知识大纲、样章和重点分布，并允许轻量调整 | P0 | 最直接提升“把资料喂给 AI 后到底发生了什么”的可控感 |
| **统一任务中心** | 把 ingest、digest、导入导出、批量判卷等长流程统一展示状态、阶段、错误和恢复入口 | P0 | 当前后端已经有后台任务与运行时状态，前端缺少统一可视化入口 |
| **统一设置中心** | 把模型、OCR/解析器、向量、搜索、调试开关收敛到一个设置面板 | P0 | 现在系统能力已变多，零散设置会越来越难维护 |
| **资料内回答 / 联网增强双模式** | Interact 支持“仅基于当前资料回答”与“允许联网补充回答”两种模式 | P0-P1 | 同时满足私有资料学习与时效信息补充，边界清晰 |
| **讲解模式 / 播放式伴读** | 不只是聊天，而是“老师分步讲一遍”，支持停顿、继续、追问、中断切回对话 | P1 | 比纯问答更像“赛博私教”，也更符合你们的伴读引擎定位 |
| **卡片化学习场景** | 把单个学习单元组织为讲解卡、例题卡、小测卡、交互卡，而不是只有文档页/聊天页/考试页 | P1 | 更容易把 Digest、Interact、Examine 真正串成闭环 |

### 2.2 暂不建议照搬的能力

以下能力不是“不好”，而是**当前不应先投入**：

- 完整的多智能体课堂秀场
- 以 PPT 舞台、角色立绘、复杂镜头和沉浸 UI 为主的外壳
- 聊天应用入口（如 OpenClaw）优先级高于站内学习闭环
- 为了支持复杂场景而提前引入大量新表或新 route

理由很简单：AITeachMe 当前最值钱的是“**私有资料 -> 知识结构 -> 伴读讲解 -> 个性化测评 -> 画像回流**”这条主链路，而不是先做一个更炫的展示层。

### 2.3 当前建议的吸收顺序

1. 先做 `构建预览 + 统一任务中心 + 统一设置中心`
2. 再做 `资料内回答 / 联网增强双模式`
3. 然后做 `讲解模式 / 卡片化学习场景`
4. 最后再评估是否需要更重的多智能体课堂外壳

## 3. 总览：LLM 在学习中的结构性优势

LLM 不是每种学习形式都有优势。以下是 LLM **真正擅长**的学习动作：

| LLM 真正擅长的 | 说明 | 传统方式做不到的原因 |
|---------------|------|---------------------|
| **从资料自动生成内容** | 给一份 PDF，自动出闪卡、题目、大纲 | 传统系统需人工出题 |
| **根据上下文即时解释** | 学生划词就能问，AI 结合教材内容回答 | 搜索引擎无法结合当前学习上下文 |
| **苏格拉底式追问** | 不给答案，一步步引导学生自己想出来 | 需要真人教师 |
| **个性化调节难度** | 根据错题和画像，动态生成适合的内容 | 传统题库是固定的 |
| **多角度解释同一概念** | 类比、例子、图示、代码、反例 | 教材只有一种讲法 |
| **批改+解释为什么错** | 不只判对错，还分析错因和思维漏洞 | 传统自动判卷只能判对错 |
| **角色扮演** | AI 扮演面试官/DBA/运维/用户 | 需要真人 |
| **总结和归纳** | 学完一段后自动总结要点和薄弱点 | 需要学生自己做 |

**LLM 不擅长的**：精确计算、代码执行、真实环境操作 → 这些用 **沙箱** 补。

## 4. P0 — 立刻可做

### 4.1 🃏 闪卡 + 间隔重复（Flashcard + Spaced Repetition）

**一句话**：AI 从知识文档自动生成记忆卡片，用遗忘曲线算法安排复习。

**为什么 LLM 有优势**：
- 传统闪卡系统需要人工制作卡片，LLM 可以从任意教材 **自动生成**
- LLM 可以针对学生的错题 **生成变式卡片**（换个问法考同一知识点）
- 复习时不只翻面看答案，LLM 可以 **追问一句** 检验是否真懂

**用户体验**：

```
[卡片正面]  什么是特征值？
[学生点击"翻转"]
[卡片背面]  矩阵 A 的特征值是满足 Av = λv 的标量 λ
[AI 追问]   "如果把 A 换成单位矩阵，特征值是多少？为什么？"
```

**技术实现**：

| 步骤 | 依赖 |
|------|------|
| Digest 从文档提取知识点 → 生成卡片 | `llm_support/` + Digest 引擎 |
| 间隔重复算法决定何时复习 | `events.py`（记录复习事件）+ `memory/` |
| 复习时 AI 追问检验 | `teaching.py` → `check_understanding` |
| 复习结果回流画像 | `events.py` → Profile 引擎 |

**间隔重复算法（SM-2 变体）**：

```
下次复习间隔 = 上次间隔 × ease_factor
ease_factor 根据答题表现调整：
  - 答对且快 → ease × 1.3
  - 答对但慢 → ease × 1.0
  - 答错     → ease × 0.6（缩短间隔，加速复习）
```

### 4.2 🗣️ AI 口试 / 答辩模式

**一句话**：AI 连续追问 3-5 个问题，像论文答辩一样层层深入，检验真实理解。

**为什么 LLM 有优势**：
- 传统考试只能考"背诵"——选择题、填空题都可以靠记忆
- 口试/答辩考的是"**你能不能用自己的话解释清楚**"
- LLM 的追问是**动态的**——学生答到哪，追问就到哪，无法提前准备答案
- **ChatGPT 代答也没用**——因为 AI 会根据前面的回答继续追问

**用户体验**：

```
AI: "请解释一下数据库的 ACID 特性。"
学生: "就是原子性、一致性、隔离性、持久性。"
AI: "好的，你说的没错。那请举一个例子说明，如果缺少'隔离性'会出什么问题？"
学生: "就是...两个人同时操作可能冲突？"
AI: "方向对了。能具体描述一个'脏读'的场景吗？"
学生: "呃...事务 A 读到了事务 B 还没提交的数据？"
AI: "非常准确！最后一问：MySQL 的 InnoDB 默认隔离级别是什么？"
```

**技术实现**：

| 步骤 | 依赖 |
|------|------|
| 根据知识点生成首问 | `teaching.py` → `generate_practice` |
| 根据学生回答动态追问 | `llm_support/` + `context.py`（注入知识+画像） |
| 判定回答质量 | `checker.py` → `check_with_llm` |
| 按 rubric 评分 | `checker.py` → Rubric |
| 记录结果 | `events.py` + `memory/` |

**Rubric 示例**：

```json
{
  "full_marks": 20,
  "criteria": [
    {"name": "概念准确性", "weight": 0.3, "description": "核心概念是否正确"},
    {"name": "举例能力", "weight": 0.3, "description": "能否用具体例子说明"},
    {"name": "深度理解", "weight": 0.2, "description": "追问下是否还能回答"},
    {"name": "表述清晰", "weight": 0.2, "description": "逻辑是否清楚"}
  ]
}
```

### 4.3 📝 概念填空式学习（Cloze Learning）

**一句话**：把知识点讲解挖空关键部分，学生填写，即时反馈。

**为什么 LLM 有优势**：
- LLM 可以从任意文本 **自动挖空**（选哪里挖空很关键，需要理解内容）
- 返回反馈时不只说"对/错"，还能解释 **为什么这里应该填这个**
- 可以根据学生填错的内容 **推测思维漏洞**

**用户体验**：

```
"HTTP 是一种 _____ 协议，默认使用 _____ 端口。
 HTTPS 相比 HTTP 增加了 _____ 层加密。"

→ 学生填写：应用层、80、SSL/TLS
→ AI：全部正确！补充：严格来说现在主流是 TLS，SSL 已经被弃用了。
```

**技术实现**：

| 步骤 | 依赖 |
|------|------|
| 从知识文档生成填空题 | `llm_support/`（LLM 选择挖空位置） |
| 判定答案 | `checker.py` → keywords 策略 |
| 解释反馈 | `teaching.py` → `explain_concept` |

### 4.4 🧭 构建预览 + 可编辑学习大纲

**一句话**：Digest 正式发布前，先给用户一个“构建预览态”，展示学习路径、样章、重点和模式判定，并允许轻量修订。

**为什么值得做**：
- 用户最常见的不安不是“AI 能不能生成”，而是“它生成的方向对不对”
- 如果正式发布前就能预览学习大纲、知识主线、重点分布，用户更愿意把大资料交给系统
- 这比单纯显示“处理中”更接近真实教学流程：先备课，再讲课

**建议体验**：

```text
Step 1: 上传资料
Step 2: AI 先给出「这是速成课 / 系统课」「预计章节」「重点主题」「样章预览」
Step 3: 用户可选择：
  - 直接构建
  - 调整学习目标
  - 锁定重点章节
  - 排除不相关文件
Step 4: 再进入正式发布
```

**技术实现**：

| 步骤 | 依赖 |
|------|------|
| 输出构建前预览态 | Digest shared prepare + `overview` |
| 产出样章/重点卡片 | Digest docs lane + graph lane 的中间状态 |
| 持久化运行时状态 | `docgen_store.py` |
| 前端展示与确认 | `/knowledge/build` + `/knowledge/docs` 现有资源组扩展字段 |

### 4.5 📋 统一任务中心与长流程状态面板

**一句话**：把 ingest、digest、导入导出、批量判卷等耗时操作统一收口到一个任务面板中。

**为什么值得做**：
- 现在系统已经不只是一两个同步请求，用户需要知道“后台到底在做什么”
- 同一个学科同时可能经历上传解析、知识构建、导出等多个流程，缺少统一面板会造成混乱
- 后端已经有后台任务注册与运行时状态基础，前端补面板的投入回报很高

**建议展示字段**：

- 任务类型：`ingest / digest / export / import / grading`
- 当前阶段：如 `prepare_shared / graph_ready / publishing`
- 进度百分比与预计剩余时间
- 最近错误信息
- 可恢复动作：重试、查看详情、跳转结果页

**技术实现**：

| 步骤 | 依赖 |
|------|------|
| 统一任务状态模型 | `BackgroundTaskRegistry` + runtime status helpers |
| 任务状态读取接口 | 优先复用现有资源组，不先拆大 job API |
| 前端任务面板 | Home / Subject 入口增加“任务中心” |

### 4.6 ⚙️ 统一设置中心

**一句话**：把模型、解析、向量、搜索、调试等配置从零散 local state 收敛到统一设置中心。

**为什么值得做**：
- 系统已经出现 LLM、OCR、embedding、rerank、web search、debug mode 等多类能力
- 继续零散配置会导致前端难维护，也不利于用户理解“当前系统到底怎么工作”
- 后续如果上 TTS / ASR / 讲解模式，这一步几乎是前置条件

**当前建议至少收敛这些项**：

- 基础：API URL、mock、debug
- 模型：主模型、轻模型、抽取模型
- 检索：向量开关、重排开关、联网补充开关
- 解析：OCR 模式、PDF provider、质量优先/速度优先
- 可观测：是否展示构建细节、诊断信息

### 4.7 🌐 资料内回答 / 联网增强双模式

**一句话**：Interact 明确区分“只按当前资料回答”和“允许联网补充资料”的两种模式。

**为什么值得做**：
- 学习私有资料时，用户往往需要强边界，不能让回答随意飘到公开网络
- 遇到时效性知识或资料缺失时，联网增强又很有价值
- 这是一种很强的产品心智：系统清楚告诉用户当前答案“来自哪里”

**建议规则**：

- `资料内模式`：只能引用 subject 内 chunks / docs / graph / profile
- `联网增强模式`：允许 web search，但必须在回答中明确区分“教材内依据”和“外部补充”
- 默认优先资料内模式，联网模式显式开启

**技术实现**：

| 步骤 | 依赖 |
|------|------|
| 检索边界控制 | `interact/retrieval.py` |
| 外部搜索 | `shared/infra/search/api.py` |
| 引用来源展示 | Chat 引用列表继续增强 |

## 5. P1 — 中期扩展

### 5.1 🎭 场景模拟 / 角色扮演

**一句话**：学生扮演某个角色（DBA / 运维 / 产品经理），在模拟场景中解决问题。

**为什么 LLM 有优势**：
- LLM 可以扮演"对面的人"——上司、用户、系统
- 场景是**动态生成**的，每次练习不重复
- 可以根据学生的操作**实时调整场景走向**
- 传统方式需要真人或预制脚本，成本高、灵活性差

**场景示例**：

| 场景 | 学生角色 | AI 角色 | 学什么 |
|------|---------|--------|--------|
| 线上故障排查 | 值班工程师 | 报警系统 + 其他同事 | Linux / Docker / 排障 |
| Code Review | 审查者 | 提交代码的同事 | 代码质量 / 最佳实践 |
| 技术面试 | 候选人 | 面试官 | 算法 / 系统设计 |
| 需求评审 | 产品经理 | 开发团队 + 用户 | 需求分析 / 沟通 |
| 数据泄露应急 | 安全工程师 | 管理层 + 系统日志 | 安全响应 / 合规 |

**技术实现**：

```python
# 场景引擎（未来可放入 workflows/support/scenarios 或独立 workflow lane）
scenario = load_scenario("db_incident")
session = await start_scenario_session(scenario, user_id="u1")

# 学生操作
response = await session.act("我先看一下数据库的慢查询日志")
# AI: "好的，以下是最近 10 分钟的慢查询：..."

response = await session.act("看起来是全表扫描导致的，我加个索引")
# AI: "你确定直接在生产环境加索引吗？会不会锁表？"

grade = session.grade()  # 按 rubric 评分
```

### 5.2 🧩 代码阅读理解

**一句话**：给学生一段代码，让学生分析输出、找 bug、提优化方案。

**为什么 LLM 有优势**：
- LLM 可以从任意代码仓库 **自动生成** 阅读理解题
- 正确答案不是唯一的，LLM 可以 **判定思路是否合理**
- 可以根据学生的编程水平 **调整代码复杂度**

**题目类型**：

| 类型 | 示例 | LLM 判定方式 |
|------|------|-------------|
| 输出预测 | "这段代码的输出是什么？" | 精确匹配 |
| Bug 发现 | "第几行有 bug？为什么？" | LLM 语义判定 |
| 复杂度分析 | "这个算法的时间复杂度是？" | 关键词匹配 |
| 优化建议 | "如何优化这段代码？" | LLM 语义判定 |
| 功能描述 | "用自然语言描述这个函数做了什么" | LLM 语义判定 |

### 5.3 📊 数据分析实验室

**一句话**：给学生数据集 + 分析需求，在沙箱里用 Python/SQL 完成分析。

**为什么 LLM 有优势**：
- LLM 判定"分析是否合理"比判定"代码是否正确"更有价值
- 可以根据学生的分析思路 **实时引导**（不直接给答案）
- 传统系统只能判"输出是否匹配"，LLM 可以判"方法是否合理"

**用户体验**：

```
题目：分析 sales.csv 中各地区的月度销售趋势，找出异常月份。

学生在 Code 沙箱中写 Python：
>>> import pandas as pd
>>> df = pd.read_csv("sales.csv")
>>> monthly = df.groupby(["region", "month"]).sum()
>>> print(monthly)

AI 反馈：你的聚合方向正确！但建议用 .agg() 替代 .sum()，
因为可以同时看均值和总额。另外，试试用 z-score 检测异常月份？
```

---

### 5.4 🗺️ 知识图谱探索学习

**一句话**：学生在图谱上点击概念节点，AI 即时讲解，按先修关系自动推荐学习顺序。

**为什么 LLM 有优势**：
- 传统知识图谱只是静态展示，LLM 可以**对图谱上的任意节点即时讲解**
- 可以根据学生的掌握状态 **高亮薄弱节点**
- 点到一个不懂的先修概念时，AI 可以**当场做一轮快速讲解**再往下走

---

### 5.5 🎬 讲解模式 / 播放式伴读

**一句话**：把 Interact 从“你问一句我答一句”升级成“AI 老师带着你讲一遍”的伴读模式。

**为什么值得做**：
- 很多学生并不会主动提问，他们更需要的是“先带我过一遍”
- 讲解模式天然适合串联 Digest 的知识结构、Examine 的即时小测和 Profile 的薄弱点
- 相比做重型课堂 UI，这更贴合 AITeachMe 的核心价值

**建议体验**：

```text
开始讲解
  -> AI 先讲当前主题
  -> 讲到关键概念暂停，抛一个追问
  -> 学生可以：
     - 继续讲
     - 让我重讲
     - 给我举例
     - 切到自由提问
  -> 结束后给出本节小结 + 小测入口
```

**实现重点**：

- 需要一个轻量播放状态机：`idle / explaining / paused / live_chat`
- 不要求先做 PPT 舞台
- 先支持文本讲解与分步推进，后续再决定是否加入语音/白板

---

### 5.6 🧱 卡片化学习场景

**一句话**：把学习体验组织成若干“场景卡片”，而不是只按页面切分功能。

**建议卡片类型**：

| 卡片 | 作用 |
|------|------|
| 讲解卡 | 总结一个概念、方法或章节 |
| 例题卡 | 给一个典型例子或推导 |
| 小测卡 | 当场检验是否理解 |
| 交互卡 | 图谱跳转、原文证据、学习计划或后续行动 |

**为什么值得做**：
- 现在文档页、聊天页、考试页相对分离，用户需要自己脑补学习路径
- 卡片化之后，一个教学单元就可以自然形成：讲解 -> 例题 -> 小测 -> 推荐复习
- 这比“直接复制 OpenMAIC 的 slide/quiz/pbl scene”更适合 AITeachMe 当前架构

**实现原则**：

1. 卡片依附现有 `teaching_unit / knowledge_node / exam template`，不先新起复杂主表
2. 页面仍可保留，但页面内部要能消费同一组卡片协议
3. 优先支持知识文档页与教学对话页共享卡片

## 6. P2 — 远期差异化

### 6.1 📖 AI 讲故事式教学

用叙事方式讲知识。例如讲"操作系统进程调度"时：

> "想象你是一个餐厅经理。现在有 10 桌客人（进程），但只有 3 个厨师（CPU 核心）。
> 你会怎么安排出菜顺序？先做前菜还是先做主菜？—— 这就是 SJF 和 FCFS 的区别。"

**LLM 优势**：动态生成故事，可以根据学生兴趣（比如喜欢游戏、体育）调整类比。

### 6.2 🎮 知识竞赛模式

类似"一站到底"，限时回答一连串问题。节奏快、有紧张感、适合复习阶段。

**LLM 优势**：自动出题、实时判定、连续升级难度。

### 6.3 📝 AI 帮你做学习笔记

学生看文档/上课时，AI 实时生成结构化笔记。学生可以标注"这里不懂"。

**LLM 优势**：从任意内容自动抽取结构化笔记，标注重点/难点。

### 6.4 🔄 错题重练 + 变式题生成

不只是把错题再做一遍，而是 **AI 生成同类型但不同细节的变式题**。

**LLM 优势**：传统题库变式题是预制的，LLM 可以无限生成变式。

### 6.5 👥 协作式学习

两个学生同时在线，AI 分配角色——一个出题一个答题，然后互换。

### 6.6 🏗️ 项目驱动学习（PBL）

给一个完整项目目标（如"搭建一个博客系统"），AI 拆解为步骤，每一步有指导和验证。
结合 sandbox 真实操作。
