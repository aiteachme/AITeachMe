# 02. 协同构建设计

## 1. 方案名称

推荐名称：

**Coordinated Dual-Lane Digest Build**

中文可以叫：

**协调型双车道 Digest 构建**

它不是一条“大一统超级图”，而是：

- 一次统一 build session
- 一个共享准备层
- 两条并行 lane
- 多个软协作点
- 一个有预算上限的一致性修复层

## 2. 设计原则

### 2.1 单次 build，对外统一

`POST /knowledge/build` 仍然是唯一入口。

对外语义不变：

- 给一批资料
- 系统开始构建 digest
- 最终得到知识文档、知识图谱、以及后续 curriculum

### 2.2 对内不做“超级串行图”

参考 `backend/app/workflows/README.md` 的分层约定：

- `services/` 负责触发
- `workflows/` 负责真正编排

因此推荐做法不是把 docgen / KG 节点都塞进一张 LangGraph，而是在 `workflows/digest/` 下新增一个更浅的 build 协调层，去调度两个已有子图。

### 2.3 共享准备层必须比现在更快，而不是更重

共享准备层只允许做：

- 必须共用的 IO
- 必须共用的规则级标准化
- 必须共用的 chunk/section identity 生成
- 必须共用的轻量 hints

不允许在共享层里加重 LLM 负担。

### 2.4 所有跨 lane 协作必须是软依赖

也就是：

- 等到就用
- 等不到就降级
- 绝不让一侧无限阻塞另一侧

### 2.5 修复必须局部化

只允许：

- 局部重抽
- 局部重审
- 局部补标签/补锚点

不允许：

- 全量重写所有章节
- 全量重抽所有 chunk
- 因一个局部冲突把整个 build 回滚重来

## 3. 顶层运行形态

## 3.1 推荐新的运行时骨架

推荐新增：

- `backend/app/workflows/digest/build/runtime.py`
- `backend/app/workflows/digest/build/state.py`
- `backend/app/workflows/digest/shared/...`

对外仍由 `knowledge_build(...)` 触发，但 service 层改为只起一个后台任务，例如：

```text
knowledge/build
  -> run_digest_build_background(...)
        -> prepare_shared_inputs(...)
        -> start doc lane
        -> start kg lane
        -> coordinate artifacts
        -> bounded reconcile
        -> publish/finalize
```

### 3.2 推荐不是“新增顶层大图”，而是“顶层协调器 + 两个子图”

原因很直接：

- docgen 子图已经天然适合 fan-out/fan-in。
- KG 子图已经天然适合流水线。
- 顶层需要的能力不是“复杂图路由”，而是“并发、artifact 同步、限时等待、补偿调度”。

这类事情用一个 async 协调器表达，比塞进单张 LangGraph 更清晰，也更不容易误串行化。

如果后续一定要补一张顶层图，也建议只做浅图：

```text
acquire_build_session
  -> prepare_shared_inputs
  -> run_dual_lane
  -> reconcile_outputs
  -> finalize
```

真正重的步骤仍然放在 docgen / KG 子图里。

## 4. 新增“共享准备层”

这是整个 merge 的核心。

### 4.1 共享准备层要产出什么

建议引入以下中间工件：

| 工件 | 作用 | docgen 是否使用 | KG 是否使用 |
| --- | --- | --- | --- |
| `SourcePacket` | 每个源文件的统一描述 | 是 | 是 |
| `NormalizedMarkdown` | 规则级统一标准化文本 | 是 | 是 |
| `TeachingMarkdown` | 仅供 docgen 的增强文本，可包含 LLM heal 结果 | 是 | 否 |
| `SectionPacket` | 按标题/question-bank 切出的稳定段落单元 | 是 | 是 |
| `digest_chunk_uid` | 跨两条 lane 的共享材料 identity | 是 | 是 |
| `FastTopicHints` | 由标题、预览、公式、question block 得到的轻量主题线索 | 是 | 是 |
| `SourceCoverageMap` | 章节/实体最终回指到哪些 section/chunk | 是 | 是 |

### 4.2 为什么要区分 `NormalizedMarkdown` 和 `TeachingMarkdown`

这是一个关键细节，不拆开会拖慢速度。

当前 docgen 的 `cleanse_node` 有更强的教学向修复能力，可能会触发 LLM heal。
当前 KG 的 `prepare_node` 只做相对轻的 `clean_markdown(...)`。

如果把 KG 强行绑定到 docgen 的 LLM heal 结果，就会有两个坏处：

1. KG 会被不必要地拖慢。
2. chunk 边界会跟着写作向修复波动，不利于稳定 evidence identity。

因此建议：

- `NormalizedMarkdown`：由共享层快速统一生成，稳定、便宜、可复用，供 KG 必用，也供 docgen 默认使用。
- `TeachingMarkdown`：只在 docgen 需要时，对 `NormalizedMarkdown` 做局部增强；KG 不等待它。

这样既能共享输入层，又不会把 KG 绑到 docgen 的最贵路径上。

### 4.3 共享准备层推荐步骤

```text
prepare_shared_inputs
  1. resolve files
  2. read markdown once
  3. normalize markdown once
  4. build section packets once
  5. materialize chunk identity map once
  6. extract fast hints once
  7. optionally start doc-only teaching heal in parallel
```

### 4.4 `SectionPacket` 应该长什么样

建议是一个轻量 sidecar，而不是 DB 模型。

```json
{
  "digest_chunk_uid": "rf_12_sec_03_abcd1234",
  "source_file_id": 12,
  "source_filename": "线性代数讲义.md",
  "chunk_index": 3,
  "title": "特征值与特征向量",
  "header_path": "第三章 > 3.2 特征值与特征向量",
  "normalized_content": "...",
  "teaching_content": null,
  "preview": "...",
  "formula_refs": ["A x = λ x"],
  "question_block_count": 0,
  "header_candidates": ["特征值", "特征向量"]
}
```

这层存在后：

- docgen 不再只能拿“整个文件内容”。
- KG 不再只能拿“落库后的 chunk id”。
- 两边终于可以围绕同一份 section identity 协作。

## 5. 双车道并行结构

## 5.1 总体结构

```text
shared prepare
  ├─ doc lane
  │    ├─ plan outline
  │    ├─ draft chapters
  │    ├─ review chapters
  │    └─ stage docs
  └─ kg lane
       ├─ hydrate chunks
       ├─ extract candidates
       ├─ cluster + resolve
       └─ finalize graph
```

关键点：

- 共享准备层之后，两个 lane 立刻并行。
- lane 之间只通过 artifact/hint 交换，不互相强等待。

## 5.2 Doc Lane 的推荐改造

当前节点与推荐改造映射如下：

| 当前节点 | 保留/改造 | 推荐新职责 |
| --- | --- | --- |
| `load_files` | 改造 | 不再直接读文件，改为 `load_shared_inputs`，从共享工件装载 `SourcePacket` / `SectionPacket` |
| `cleanse` | 改造 | 只做 doc 专属 `TeachingMarkdown` 增强，不再重复基础清洗 |
| `outline_map` | 增强 | 直接消费共享层已有的 `header_candidates` / `preview` / `formula_refs` |
| `outline_reduce` | 增强 | 引入 `FastTopicHints` 和 KG 早期 topic anchors 作为 soft priors |
| `draft_chapter` | 增强 | 章节输入不再只是 raw source text，还包含稳定 `source_chunk_ids` |
| `review_chapter` | 增强 | 增加“graph coverage / orphan concept”校验，但只做局部提示，不变成图谱依赖 |
| `extract_metadata` | 小改 | tags 可与 graph/topic anchors 对齐 |
| `finalize_assemble` | 拆分 | 拆成 `stage_docs` + `publish_docs`，为一致性修复预留窗口 |

### 5.2.1 `outline_reduce` 如何利用图谱相关线索

这里不要直接等完整 KG。

更合理的做法是：

1. 共享准备层先产出 `FastTopicHints`
   - 基于标题候选
   - 基于 header path
   - 基于公式/题块信号
2. KG lane 在 `extract` 的早期，也可以增量发布一个 `TopicAnchorSnapshot`
   - 仅包含高频 Topic/Concept 名称
   - 不要求 resolved node id
3. `outline_reduce` 将它们视作 soft priors，而不是硬约束

例如：

- 共享层和 KG 早期都显示高频主题是“矩阵”“线性变换”“特征值”
- docgen 大纲规划时就不容易把这三块混成一章杂糅大杂烩

### 5.2.2 `review_chapter` 如何真正和 KG 协作

不是让 review 去查整张图，而是给它一个非常轻的 coverage contract：

```json
{
  "chapter_index": 2,
  "chapter_title": "特征值与特征向量",
  "expected_concepts": ["特征值", "特征向量", "相似对角化"],
  "missing_concepts": ["相似对角化"],
  "orphan_examples": ["Question 12: ..."],
  "source_chunk_ids": ["rf_12_sec_03_abcd1234", "rf_12_sec_04_efgh5678"]
}
```

review 只需要回答：

- 本章是否明显漏讲了高频概念？
- 是否例子很多但概念框架不清？
- 是否标签与章节主题偏离？

这样可以提升文档质量，但不会把审校变成重型 graph query。

## 5.3 KG Lane 的推荐改造

当前节点与推荐改造映射如下：

| 当前节点 | 保留/改造 | 推荐新职责 |
| --- | --- | --- |
| `acquire_lock` | 改造 | 支持“继承顶层 build session lock”，避免双锁割裂 |
| `prepare` | 重写重点 | 不再重复读 markdown/重复切分，而是消费共享 `SectionPacket`，必要时再物化 `DocumentChunk` |
| `extract` | 增强 | 允许带入 doc outline 的章节先验，但只能作为 taxonomy hint |
| `cluster` | 增强 | 对同章高频主题可给更高聚类先验，但不替代 embedding/语义判断 |
| `resolve_nodes` | 保留主逻辑 | 仍以 normalized_name / alias / embedding + LLM 为准 |
| `resolve_edges` | 保留主逻辑 | 仍以 evidence + resolved endpoints 为准 |
| `analyze_impact` | 保留 | 仍只基于 graph delta |
| `finalize_graph` | 小改 | 增加与 build session 的协调回调，但默认不等待 doc publish |

### 5.3.1 KG 不应该被 doc outline 强行牵着走

章节大纲只适合作为 soft taxonomy prior。

能做的：

- 某些 `section title` 提供 parent topic 候选。
- 某些 chapter title 帮助降低 topic 命名漂移。

不能做的：

- 因为文档把两件事写在同一章，就强行把两个实体 merge。
- 因为文档标题用了一个教学口语化名字，就直接覆盖 canonical name。

### 5.3.2 KG 最值得利用 doc lane 的地方

不是 resolved identity，而是“教学组织线索”。

例如：

- 章节边界说明了哪些概念经常一起出现，可以作为 `taxonomy_hint`。
- section title 可以改善 `Topic` 命名。
- 某章节的大量公式、例题集中在一起时，可以帮助识别 `Method` 与 `Example` 的父子关系。

## 6. 推荐的跨 lane 协作点

下面这几处是值得做的，而且不会明显拖慢速度。

## 6.1 协作点 A：共享层产出 `FastTopicHints`

**谁生产：** 共享准备层  
**谁消费：** doc lane `outline_reduce`，KG lane `extract`  
**成本：** 很低，主要是规则抽取与轻量聚合  

作用：

- 减少 doc 大纲乱切。
- 减少 KG 主题命名漂移。

## 6.2 协作点 B：doc 大纲向 KG 发布 `ChapterPriors`

**谁生产：** doc lane `outline_reduce`  
**谁消费：** KG lane `extract` / `cluster`  
**成本：** 很低，只是 sidecar 工件  

建议只提供：

- `chapter_title`
- `section_titles`
- `source_chunk_ids`

不要提供：

- 章节正文
- 教学性总结

## 6.3 协作点 C：KG 早期提取向 doc 发布 `TopicAnchorSnapshot`

**谁生产：** KG lane `extract` 的早期增量聚合  
**谁消费：** doc lane `review_chapter` / `metadata`  
**成本：** 中低，只是从已有抽取结果做轻量汇总  

建议包含：

- 高频 Topic / Concept 名称
- 出现频率
- source chunk 覆盖

不要求：

- 已 resolved 的 node id
- 最终 graph status

## 6.4 协作点 D：一致性校验器生成 `CoverageReport`

**谁生产：** 顶层 build 协调器  
**谁消费：** doc patch / kg patch / observability  
**成本：** 低到中，主要是比对已有工件  

建议输出：

- 文档章内高频术语但图谱无覆盖
- 图谱高置信度节点但文档无覆盖
- orphan example rate
- chapter/topic misalignment
- evidence density per chapter

## 6.5 协作点 E：局部修复

只允许两种：

1. `doc_patch`
   - 只重审/重写受影响章节
2. `kg_patch`
   - 只重抽受影响 section/chunk

并且必须有预算上限，例如：

- 最多修 2 个章节
- 最多重抽 4 个 chunks
- 最多额外 3 次 LLM 调用

## 7. 一致性校验器应该怎么设计

## 7.1 不做“哲学判断”，只做结构化比对

建议从四类信号入手：

1. **coverage gap**
   - 文档讲了，图谱没有
   - 图谱有了，文档没讲
2. **taxonomy drift**
   - 文档章节组织与 graph topic 边界明显错位
3. **orphan signals**
   - Example/Definition 很多，但没有 Concept/Method 支撑
4. **evidence weakness**
   - 某些章节/节点只有极薄的 source coverage

## 7.2 推荐最小规则集

### 规则 1：章节核心词缺图谱锚点

输入：

- `chapter_title`
- `section_titles`
- `tags`
- `TopicAnchorSnapshot`

如果一章里高频标题词在图谱锚点覆盖率很低，就标记为：

- `doc_over_graph_gap`

### 规则 2：高置信度 graph node 无文档归属

输入：

- `resolved nodes`
- `source_chunk_ids`
- `chapter assignments`

如果一个高置信度 node 来自若干 `source_chunk_ids`，但这些 chunk 没有被任何章节稳定覆盖，就标记为：

- `graph_over_doc_gap`

### 规则 3：Example/Definition 孤儿率异常

如果某一章相关 chunks 中：

- `Example` 或 `Definition` 很多
- 但父 `Topic / Concept / Method` 很薄弱

则标记为：

- `orphan_teaching_structure`

这通常意味着：

- 文档需要补概念框架
- 或图谱需要补父节点抽取

### 规则 4：章节名与 topic 名严重分裂

如果同一批 `source_chunk_ids`：

- 文档命名集中在 A
- 图谱命名集中在 B
- A/B 语义相距较大

则标记为：

- `taxonomy_drift`

## 8. 性能设计：怎样保证不变慢

这是整个方案里最重要的约束。

## 8.1 绝不增加“全量额外 pass”

不允许：

- 每个 chunk 因 merge 再跑一次抽取
- 每个章节因 merge 再跑一次写作

允许的只有：

- 共享已经存在的工件
- 有预算上限的局部修复

## 8.2 协作必须是“等不到就降级”

建议给关键协作点设置超时：

| 协作点 | 等待策略 |
| --- | --- |
| `FastTopicHints -> outline_reduce` | 不等待，准备层完成即有 |
| `ChapterPriors -> KG extract` | 0ms 软读取，读不到直接继续 |
| `TopicAnchorSnapshot -> doc review` | 最多等待一个很小 budget，比如 300-500ms |
| `CoverageReport -> publish_docs` | 最多等待一个小 budget，比如 500-800ms |

这样可以保证：

- doc 主路径不被 KG 卡死
- KG 主路径不被 doc 卡死

## 8.3 把最贵的步骤继续留在各自 lane 内

docgen 继续最贵的是：

- 章节写作
- 章节审校

KG 继续最贵的是：

- chunk 抽取
- node resolve

共享层不应该引入与这些同量级的新重活。

## 8.4 共享层只做“本来就该做一次”的事

共享层收益最大的就是替换掉以下重复劳动：

- 文件读取两次
- 基础 clean 两次
- chunk/section 切分两次
- 标题/预览轻提示分别做两次

这部分只要做对了，理论上不是变慢，反而应该略快。

## 9. 推荐的新工件与目录布局

考虑到当前系统已经大量使用 subject 级本地目录与 staging 目录，建议继续沿用本地工件风格。

示意：

```text
data/<subject>/digest_builds/<session_id>/
  shared/
    source_manifest.json
    source_packets.json
    section_packets.json
    fast_topic_hints.json
    chapter_priors.json
    topic_anchor_snapshot.json
    coverage_report.json
  docs/
    stage/
      chapter_01_*.md
      ...
  graph/
    stage/
      extract_snapshot.json
      resolve_snapshot.json
```

其中：

- event bus 只负责“通知工件已就绪”。
- 实际 payload 优先走共享工件文件，不在 event 中塞大对象。

这和当前 `docgen_intermediate/latest/`、`knowledge_docs/_building/` 的风格是一致的。

## 11. 一个具体例子

假设资料域是“线性代数期末复习”。

共享准备层先得到：

- section titles：`矩阵基础`、`线性变换`、`特征值与特征向量`
- formula refs：`A x = λ x`
- question chunks：若干题目块

随后：

1. doc lane 用这些 hints 规划出 4 章大纲，不再把“线性变换”和“特征值”揉成一个大章。
2. KG lane 在抽取时，看到 `ChapterPriors`，会更倾向把相关定义和方法挂到“线性变换/特征值”附近，而不是生成漂移 topic 名。
3. KG 早期抽取发现“相似对角化”频率很高。
4. doc review 阶段发现相关章节几乎没写“相似对角化”，于是发出缺口警告。
5. 一致性校验器判断这是一个局部缺口，只重审这一章，并要求补入该概念的定义与条件。

结果是：

- 文档更像教学材料，而不是平铺摘要。
- 图谱的 topic 命名与章节结构更稳定。
- 二者可以互相校验，不再各说各话。

## 12. 最终推荐

如果只保留一句设计决策，那就是：

**用“共享准备层 + 双车道并行 + 软协作 + 局部一致性修复”来合并 docgen 与 KG，而不是把两条 LangGraph 暴力串成一条。**

这是当前代码现实下，既能保住速度，又能让两边一起变好的最稳方案。
