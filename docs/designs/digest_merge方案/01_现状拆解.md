# 01. 现状拆解

## 1. 范围与判断标准

这份拆解只看当前仓库里已经存在的真实实现，不按理想状态脑补。

主要依据：

- `backend/app/api/knowledge.py`
- `backend/app/services/knowledge/digest_service.py`
- `backend/app/workflows/digest/runtime.py`
- `backend/app/workflows/digest/docs/*`
- `backend/app/workflows/digest/kg/*`
- `backend/app/workflows/README.md`
- `docs/designs/05_digest_engine.md`

判断标准有两个：

1. 现状里两条流程到底共享了什么、没共享什么。
2. 如果要合并，哪里可以共用，哪里绝对不能硬绑在一起。

## 2. 当前入口其实已经像“一个 build”

### 2.1 API 层行为

`backend/app/api/knowledge.py` 中的 `knowledge_build(...)` 当前会做三件事：

1. 校验 subject。
2. 调用 `trigger_docgen_build(...)` 选择本次可接受的 source files。
3. 在 `BackgroundTasks` 中同时加入：
   - `run_docgen_background(...)`
   - `run_graph_digest_background(...)`

也就是说，对前端来说它已经像是一个统一 build。

### 2.2 但 service/runtime 层仍是双轨

`backend/app/services/knowledge/digest_service.py` 里：

- `run_docgen_background(...)` 只关心 docgen workflow 和 doc 发布锁。
- `run_graph_digest_background(...)` 只关心 graph workflow 的 job/run id。

`backend/app/workflows/digest/runtime.py` 里：

- `run_docgen_workflow(...)` 只编排 docs graph。
- `run_graph_digest_workflow(...)` 只编排 kg graph，并在 finalize 后触发 curriculum。

结论：

- 现在统一的是 API 触发。
- 没有统一的是内部 build session、共享输入层、共享中间工件、共享校验层。

## 3. 当前 DocGen 图的真实结构

文件：`backend/app/workflows/digest/docs/graph.py`

当前 docgen graph：

```text
load_files
  -> cleanse
  -> outline_map
  -> outline_reduce
  -> Send xN -> draft_chapter
  -> collect_drafts
  -> Send xN -> review_chapter
  -> collect_reviews
  -> Send xN -> extract_metadata
  -> finalize_assemble
```

### 3.1 DocGen 状态粒度

文件：`backend/app/workflows/digest/docs/state.py`

当前 `DocGenState` 关键字段：

- 输入侧：`subject`、`file_ids`、`user_prompt`、`requested_at`
- 原始材料：`raw_chunks`
- 清洗材料：`clean_chunks`
- 大纲：`local_outlines`、`outline_tree`、`chapter_assignments`
- fan-out 累积结果：`chapter_drafts`、`chapter_reviews`、`chapter_metadatas`
- 指标：`draft_ms`、`review_ms`、`metadata_ms`、`llm_calls_total`、`llm_calls_skipped`
- 终态：`doc_ids`、`merged_markdown`、`merged_path`

这说明 docgen 当前的工作单元本质上是：

- 前半段按文件聚合。
- 中间按章节 fan-out。
- 最后再回收为 merged 文档。

### 3.2 每个节点到底在做什么

| 节点 | 当前真实职责 | 关键输入 | 关键输出 | 性能敏感点 |
| --- | --- | --- | --- | --- |
| `load_files` | 直接从 `RawFile.markdown_path` 读 markdown | `file_ids` | `raw_chunks` | 文件 IO |
| `cleanse` | 先规则清洗，再按策略决定是否做 LLM heal | `raw_chunks` | `clean_chunks` | LLM cleanse 开销 |
| `outline_map` | 从 clean markdown 中抽标题/预览 | `clean_chunks` | `local_outlines` | 轻量，基本不是瓶颈 |
| `outline_reduce` | 调 `generate_global_outline(...)` 生成全局章节树，再构造 `chapter_assignments` | `local_outlines` | `outline_tree`、`chapter_assignments` | 一次 LLM 全局规划 |
| `draft_chapter` | 按章节写正文 | `chapter_assignments` | `chapter_drafts` | 章节级 LLM，受 `max_parallel_chapters` 限制 |
| `review_chapter` | 审校，不通过则整章重写一次 | `chapter_drafts` | `chapter_reviews` | 额外 LLM pass，可能双倍成本 |
| `extract_metadata` | 提取 summary/tags | `chapter_reviews` | `chapter_metadatas` | 轻量 |
| `finalize_assemble` | 生成 merged，落盘 staging/publish，重建 `KnowledgeDoc` | `chapter_metadatas` | `doc_ids`、`merged_markdown` | 文件写入与最终发布 |

### 3.3 DocGen 当前的关键现实

1. 它并不依赖 `DocumentChunk`。
2. 它直接从 markdown 文件读内容。
3. 它已经有比较明确的性能策略：
   - `docgen_max_parallel_chapters`
   - `docgen_io_parallelism`
   - `skip_llm_cleanse_for_clean_markdown`
   - `skip_llm_review_for_single_chapter`
4. 它已经是一个“章节级 fan-out”系统，速度主要靠并发章节写作撑住。

## 4. 当前 KG 图的真实结构

文件：`backend/app/workflows/digest/kg/graph.py`

当前 KG graph：

```text
acquire_lock
  -> prepare
  -> extract
  -> cluster
  -> resolve_nodes
  -> resolve_edges
  -> analyze_impact
  -> finalize_graph
```

失败时进入 `fail`。

### 4.1 KG 状态粒度

文件：`backend/app/workflows/digest/kg/state.py`

当前 `KGDigestState` 关键字段：

- 输入：`subject`、`file_ids`、`job_id`
- 准备结果：`chunk_ids`
- 提取结果：`candidates`、`all_candidate_edges`
- 聚类/解析：`clustered_candidates`、`candidate_name_to_cluster_id`
- 对齐结果：`candidate_name_to_resolved_node_id`、`cluster_id_to_resolved_node_id`
- 图谱变化：`new_node_ids`、`updated_node_ids`、`new_edge_ids`、`updated_edge_ids`
- 下游影响：`impact_set`
- 运行控制：`lock_acquired`、`error`

KG 的工作单元本质上是：

- 先把文件物化成 `Document` / `DocumentChunk`
- 再按 chunk 做实体/关系提取
- 再做 batch 范围内聚类与对齐
- 最后把变更落成图谱和 impact

### 4.2 每个节点到底在做什么

| 节点 | 当前真实职责 | 关键输入 | 关键输出 | 性能敏感点 |
| --- | --- | --- | --- | --- |
| `acquire_lock` | 抢 graph subject build lock | `subject`、`job_id` | `lock_acquired` | 不是主耗时 |
| `prepare` | 读取 ready raw files，必要时物化 `Document` / `DocumentChunk` / embeddings | `file_ids` | `chunk_ids` | 文件读取、chunking、embedding |
| `extract` | 对每个 chunk 跑候选实体/关系抽取 | `chunk_ids` | `candidates`、`all_candidate_edges` | 逐 chunk LLM，是重耗时 |
| `cluster` | batch 内聚类候选实体 | `candidates` | `clustered_candidates` | embedding/相似度 |
| `resolve_nodes` | 与已有图谱做 exact/alias/semantic 对齐 | `clustered_candidates` | resolved mappings | 逐 cluster embedding + LLM judge |
| `resolve_edges` | 创建或更新边 + evidence | `all_candidate_edges` | edge ids | DB 写入与 commit 频率 |
| `analyze_impact` | 计算 curriculum 受影响范围 | graph delta | `impact_set` | 中等 |
| `finalize_graph` | 激活 pending graph entities，释放 lock，触发 curriculum | graph delta | 完成态 | 不是主耗时 |

### 4.3 KG 当前的关键现实

1. KG 已经拥有“材料标准化”的一部分能力：
   - `load_clean_markdown(...)`
   - `clean_markdown(...)`
   - `chunk_markdown(...)`
   - `ensure_document_chunks_for_file(...)`
2. KG 处理粒度更细，是 chunk/实体级。
3. KG 当前完全不知道 docgen 的章节规划，也不知道某个章节写了什么。
4. KG 的主耗时不是 finalize，而是 `prepare` 的 embeddings、`extract` 的逐 chunk 抽取、`resolve_nodes` 的对齐。

## 5. 当前两条流程的断层在哪里

### 5.1 同一份 markdown 被处理了两次

docgen 路径：

- 直接读 `RawFile.markdown_path`
- 自己做 `rule_based_cleanse + stitch_sentences`
- 在自己的 `clean_chunks` 结构里继续走

KG 路径：

- 也从 `RawFile.markdown_path` 读
- 自己做 `clean_markdown`
- 再 `chunk_markdown`
- 再落 `DocumentChunk`

这带来几个问题：

- 重复读文件。
- 重复清洗。
- docgen 用的“clean chunk”与 KG 用的 `DocumentChunk` 不是同一 identity。
- 最后无法自然回答“这个章节到底对应哪些 chunk / 哪些 graph evidence”。

### 5.2 粒度不一致，但没有桥梁层

docgen 的结构：

- 文件
- 章节
- section payload

KG 的结构：

- document
- chunk
- candidate node / edge

问题不是粒度不同本身，而是当前没有中间桥梁层。

缺的其实是一个共享的、足够轻的材料标准层，例如：

- `SourcePacket`
- `SectionPacket`
- `digest_chunk_uid`
- `source_chunk_ids`

只要这层存在，章节和图谱就能对到同一份材料；没有这层，它们永远只能“各做各的”。

### 5.3 中途完全没有协作

现在 docgen 不知道：

- KG 在 chunk 里提到了哪些高频 Topic / Concept / Method
- 哪些例题/定义在 KG 看来是孤儿
- 某个章节是否遗漏了高频核心概念

现在 KG 也不知道：

- docgen 最终把材料组织成了哪些章节
- 某些 section title 能不能作为 taxonomy soft priors
- 哪些概念在文档里被聚成了同一教学单元

### 5.4 最终没有一致性校验

现在完全可能出现：

- 文档里某章花了大量篇幅讲“特征向量”，KG 里却没有对应 node。
- KG 里抽出了一批高置信度 Method / Concept，文档却几乎没有覆盖。
- 文档章节边界和图谱 topic 边界严重错位，但系统没有任何报警。

### 5.5 锁与完成边界也不统一

现在：

- docgen 有自己的 build lock 和 staging/publish 生命周期。
- KG 有自己的 subject build lock 和 job 生命周期。
- curriculum 只挂在 KG finalize 后面。

这意味着：

- 对外用户以为是一次 digest build。
- 对内其实是两个完成时刻、两套失败语义、两套中间状态。

## 6. 现在可以共享什么，不能共享什么

### 6.1 可以共享的部分

这些是最自然的 merge 点：

1. **原始文件读取**
   - 两边都从同一批 `RawFile.markdown_path` 开始。
2. **规则级标准化**
   - 规范换行、标题空格、空行压缩、基础噪声清理。
3. **chunk / section 切分**
   - 当前 `chunk_markdown(...)` 已经能按标题和题库块切分。
4. **轻量提示信号**
   - 标题候选
   - chunk preview
   - 公式线索
   - question block 结构
5. **材料 identity**
   - 至少需要一个贯穿 docgen 与 KG 的稳定 `chunk uid / source chunk id`。

### 6.2 不能直接共享的部分

这些不能被粗暴共用：

1. **docgen 的章节正文**
   - KG 不应该依赖 LLM 写出的文案来建图谱。
2. **KG 的 resolved graph identity**
   - docgen 不应该在早期强依赖已落库图谱，否则会被对齐与 finalize 时机拖慢。
3. **整条执行顺序**
   - 不能要求“先跑完 KG 再写文档”，也不能要求“先写完文档再建 KG”。

## 7. 哪些“看起来像 merge”的方向其实不对

### 7.1 先 KG 后 DocGen

直觉上很诱人，因为图谱好像更结构化。

但它的问题很大：

- KG 当前最慢的部分是逐 chunk 抽取与对齐。
- docgen 的大纲生成会被强制等待 KG 完整结果。
- 这会直接拉长文档生成首包时间。

### 7.2 先 DocGen 后 KG

这也不对：

- 文档章节是教学组织结果，不是知识 identity。
- 用章节去强行驱动图谱，会把写作偏好误当成实体边界。
- KG 还会失去自己的 chunk 级证据优势。

### 7.3 一条超级 LangGraph

把所有节点塞进一张图里，表面上统一，实际上更糟：

- docgen 是 fan-out fan-in 结构。
- KG 是 chunk/cluster/resolve 的流水结构。
- 二者失败语义、并发模式、回滚范围都不同。
- 一旦强行合图，很容易把可并行的步骤串行化。

这条路最大的风险不是“代码不好看”，而是**速度一定变差**。

## 8. 性能约束必须先写死

用户已经明确提出，merge 不能拖慢两边。

基于当前实现，必须遵守下面这些性能约束：

1. 不能给每个 chunk 再多加一轮额外 LLM pass。
2. 不能给每个章节再多加一轮额外强依赖 LLM pass。
3. 不能让 docgen 在主路径上等待 KG finalize。
4. 不能让 KG 在主路径上等待 docgen publish。
5. 协作必须以“共享已有工件”和“限额局部修复”为主，不能以“全量重跑”为主。

## 9. 从现状推出的正确方向

基于上面这些事实，最合理的方向不是“把两条图并成一条”，而是：

### 9.1 新增一个共享准备层

这一层只做二者都会用到的事情：

- 读取 source files
- 做统一的基础标准化
- 生成稳定 chunk/section identity
- 产出轻量 hints

### 9.2 保留两条 lane 的专长

- doc lane 继续负责教学表达、章节组织、写作与审校。
- KG lane 继续负责 chunk 级证据、实体/关系对齐、impact 回流。

### 9.3 在 lane 之间增加软协作

例如：

- 文档大纲规划时，拿到 fast topic hints。
- 图谱聚类/对齐时，拿到章节 taxonomic priors。
- 文档审校和最终发布前，拿到 graph coverage report。

### 9.4 最后再做有预算上限的一致性修复

关键是“局部修复”，不是“再跑一遍全量 build”。

比如：

- 只重抽 2-3 个疑似遗漏 chunk。
- 只重审 1-2 个覆盖率异常章节。

这才是后续架构应该去的方向。
