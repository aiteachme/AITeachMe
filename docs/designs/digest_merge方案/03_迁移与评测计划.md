# 03. 迁移与评测计划

## 1. 迁移原则

目标不是一次性重做整个 digest，而是按最小风险路径逐步收敛到协同构建。

迁移时要优先保证三件事：

1. `knowledge/build` 外部协议不变。
2. docgen 与 KG 的现有主结果先保持可用。
3. 每一阶段都能独立验证“没有明显变慢”。

## 2. 建议按四个阶段推进

## 2.1 Phase A：共享准备层落地

### 目标

先解决最确定的重复劳动问题。

### 要做的事

- 新增统一 `digest build session` 入口。
- 把文件读取、基础标准化、chunk/section 切分、轻量 hints 提取移到共享层。
- docgen 和 KG 都改成先消费共享层工件。

### 这一阶段先不要做的事

- 不做复杂双向修复。
- 不改变 KG resolved identity 逻辑。
- 不改变 docgen writer/reviewer prompt。

### 验收标准

- 相同 source files 不再被两边重复读取和重复规则清洗。
- 两边都能拿到稳定 `digest_chunk_uid` / `source_chunk_ids`。
- 主体结果与当前版本一致性基本可接受。

## 2.2 Phase B：中途软协作落地

### 目标

让两条 lane 开始真正“互相看见对方”。

### 要做的事

- 共享层输出 `FastTopicHints`。
- doc `outline_reduce` 发布 `ChapterPriors`。
- KG `extract` 增量发布 `TopicAnchorSnapshot`。
- doc `review_chapter` 开始消费轻量 coverage signals。

### 验收标准

- 文档章节命名漂移下降。
- 图谱 topic 命名漂移下降。
- 高价值章节的概念漏讲率下降。

## 2.3 Phase C：一致性校验与局部修复

### 目标

让系统不再只是“都跑完了”，而是“互相核过了”。

### 要做的事

- 新增 `CoverageReport` 生成。
- doc finalize 拆成 `stage_docs` 与 `publish_docs`。
- 增加 `doc_patch` / `kg_patch` 能力，但必须有限额。

### 验收标准

- 能发现明显文档/图谱错位。
- 能用局部修复解决一部分缺口。
- 不出现因为一个小缺口导致全量重跑的情况。

## 2.4 Phase D：可观测性与长期评测

### 目标

把“看起来更好”变成“被持续量化地证明更好”。

### 要做的事

- 补齐 build 级 latency 分解。
- 补齐文档/图谱一致性指标。
- 建立固定评测资料集与回归集。
- 给每个修复动作记账，知道它值不值得。

## 3. 推荐的功能开关

迁移时建议显式加 feature flags：

| 开关 | 作用 |
| --- | --- |
| `digest_shared_prepare_enabled` | 是否启用共享准备层 |
| `digest_chapter_priors_enabled` | 是否让 doc 向 KG 发布章节先验 |
| `digest_topic_anchor_enabled` | 是否让 KG 向 doc 发布主题锚点 |
| `digest_consistency_report_enabled` | 是否生成一致性报告 |
| `digest_local_patch_enabled` | 是否启用局部修复 |

这样可以做到：

- 出问题快速降级
- 逐步放量
- 对比新旧路径指标

## 4. 必须跟踪的性能指标

## 4.1 build 时延分解

建议至少记录：

- `shared_prepare_ms`
- `doc_lane_total_ms`
- `kg_lane_total_ms`
- `doc_outline_ms`
- `doc_draft_ms`
- `doc_review_ms`
- `kg_prepare_ms`
- `kg_extract_ms`
- `kg_cluster_ms`
- `kg_resolve_nodes_ms`
- `reconcile_ms`
- `patch_ms`

### 关键判断

真正要看的不是单点耗时，而是：

- 合并后 P50 / P90 总时长
- doc lane 是否被拉慢
- KG lane 是否被拉慢
- reconcile / patch 是否经常失控

## 4.2 性能红线

建议先写成明确目标：

1. 共享层上线后，总 build P50 不应明显高于当前 `max(docgen, KG)`。
2. 中途软协作上线后，总 build P90 增幅最好控制在一个很小的区间。
3. patch 路径命中率如果很低，但成本很高，就要及时下线。

## 5. 必须跟踪的质量指标

## 5.1 文档质量指标

建议关注：

- 章节结构完整率
- 标题/section 稳定性
- 核心公式保留率
- 审校失败率
- 章节重写率

## 5.2 图谱质量指标

建议关注：

- 每次 build 的高置信度新节点数
- orphan example / definition 比率
- alias 漂移率
- node / edge evidence 密度
- graph 命名稳定性

## 5.3 文档-图谱协同指标

这是新增的重点：

- `doc_over_graph_gap_rate`
- `graph_over_doc_gap_rate`
- `taxonomy_drift_rate`
- `chapter_coverage_score`
- `node_doc_alignment_score`
- `local_patch_success_rate`

如果这些指标长期没有改善，那么 merge 只是架构重组，不是质量升级。

## 6. 推荐的评测集设计

至少应覆盖三类资料：

### 6.1 课程型讲义

例如：

- 大学课程 PPT
- 教材章节 markdown
- 复习提纲

适合看：

- 章节规划是否稳定
- 概念树是否完整

### 6.2 题库型资料

例如：

- 选择题/填空题题库
- 历年真题

适合看：

- question-bank chunking
- Example 与 Topic / Concept 的挂接质量

### 6.3 混合型资料

例如：

- 讲义 + 例题 + 答案

适合看：

- 文档与图谱是否都能处理“讲解 + 题目”混合材料
- orphan example 是否下降

## 7. 工程层面的注意事项

## 7.1 不要一下子重写现有子图

最稳的方式是：

- 先在 shared prepare 前后加新层
- 让 docgen / KG 子图先“换输入，不换核心职责”
- 等共享 identity 与 sidecar 工件稳定后，再慢慢增强协作点

## 7.2 不要把 patch 设计成默认主路径

patch 应该是：

- 异常时触发
- 局部时触发
- 有预算时触发

如果 patch 变成经常性的主路径，说明前面的 outline / extract / resolve 做得还不够好。

## 7.3 curriculum 不要过早卷进来

当前 KG finalize 后会触发 curriculum。

这条链路在前几阶段最好维持现状：

- 不要让 curriculum 依赖 doc publish
- 不要让 doc patch 直接阻塞 curriculum

否则会把 digest merge 的问题扩散成全链路问题。

## 8. 最重要的红线

这几条如果踩了，说明方案跑偏了：

1. 合并后 docgen 必须等完整 KG 才能出文档。
2. 合并后 KG 必须等文档 publish 才能 finalize。
3. 为了协作而给每个 chunk/章节多加了一轮默认 LLM pass。
4. 一致性修复经常演变成全量重跑。
5. 最终虽然代码更“统一”了，但 build 更慢、问题更隐蔽、质量也没有明显提升。

## 9. 最终验收问题

到真正准备收口时，可以只问下面五个问题：

1. 相同资料是否只被标准化一次？
2. 文档章节与图谱节点是否终于能通过共享 chunk identity 对齐？
3. 两条 lane 是否真的发生了中途协作，而不是只在最后拼一下结果？
4. 一致性缺口是否能被发现，并且常见问题能被局部修复？
5. 整体速度是否基本守住了当前水平？

如果这五个问题里有三个答不上来，就说明这次 merge 还不算成功。
