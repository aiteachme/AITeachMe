# 05. Digest 引擎

## 1. 目标与职责
Digest 引擎是 AITeachMe 的知识组织层，负责把已经规范化的学习材料组织成教学系统可以长期复用的结构化知识。

它不只是“做个总结”，而是要完成四类更核心的任务：

- 建立知识实体、关系与证据链
- 把知识图谱整理成适合教学的中间粒度
- 派生展示型课程视图
- 派生学习顺序型课程视图

从系统位置看，Digest 位于 Ingest 与 Interact / Examine / Profile 之间，是全局的知识中枢。

---

## 2. 当前实现落点

当前代码里，Digest 主要落在以下位置：

- 前端页面与组件：`SummaryPage`、图谱视图、主题树视图、DAG 视图、证据弹窗
- 后端资源组：`knowledge`
- 业务编排：`digest_service.py`、`curriculum_service.py`、`graph_query_service.py`
- Agent 与工作流：`agents/digest/*`
- 核心模型：知识图谱、Teaching Unit、课程版本对象、构建任务对象

Digest 已经不是概念层设计，而是当前代码里最复杂、最核心的一层。

## 3. Pipeline 设计

### 3.1 知识构建主 Pipeline

| 步骤 | 子模块 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1. 构建触发 | `digest_service.trigger_digest_build` | `subject`、`file_ids`、可选幂等键 | `GraphDigestJob` |
| 2. 材料准备 | `kg_workflow.prepare` | `Document`、`DocumentChunk`、已有图谱状态 | 待抽取 chunk 集合、构建上下文 |
| 3. 候选抽取 | `kg_extractor.extract_candidates` | 单个或批量 chunk | 候选节点、候选边、证据绑定 |
| 4. 批内聚类 | `kg_clusterer` | 候选节点/边、名称与语义相似度 | 候选簇、代表项 |
| 5. 实体对齐 | `kg_resolver.resolve_node / resolve_edge` | 候选簇、现有图谱、embedding | 新实体或新修订决策 |
| 6. 证据写回 | `kg_workflow.finalize_graph` | 对齐结果、证据来源 | 节点、边、修订、EvidenceLink |
| 7. 影响分析 | `kg_impact_analyzer.analyze_impact` | 新旧图谱差异 | 受影响节点、单元、树、DAG 范围 |
| 8. 图谱收尾 | `run_kg_digest_workflow` | 图谱增量结果、任务状态 | 完成态 `GraphDigestJob` |
| 9. 单元派生 | `unit_builder.derive_teaching_units` | 当前图谱、局部关系、embedding | `TeachingUnit` 集合 |
| 10. 主题树派生 | `theme_tree_builder.derive_theme_tree` | 单元、锚点、历史挂载 | `ThemeTreeVersion` |
| 11. 先修图派生 | `prereq_dag_builder.derive_prereq_dag` | 单元、图中依赖、影响范围 | `PrereqDagVersion` |
| 12. 快照发布 | `curriculum_workflow.finalize` | Tree、DAG、单元版本 | `CurriculumSnapshot` |

### 3.2 查询与消费 Pipeline

| 步骤 | 子模块 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1. 选择查询视图 | `SummaryPage` / 组件层 | 用户想看图谱、单元、树、DAG、证据 | 具体查询类型 |
| 2. 数据读取 | `graph_query_service` / `curriculum_service` | subject、查询条件、对象 ID | 节点列表、单元列表、树、DAG、快照 |
| 3. 细节展开 | `get_graph_node_detail` / `get_evidence_context` / `get_teaching_unit_detail` | 节点 ID、证据 ID、单元 ID | 详情数据、原文上下文 |
| 4. 前端消费 | 图谱视图、树视图、证据弹窗 | 查询结果 | 可视化展示、跳转、进一步问答入口 |

### 3.3 关键子模块输入输出

- 材料准备模块
  输入：`Document`、`DocumentChunk`、subject 当前构建状态。
  输出：待处理 chunk 集合、构建初始状态。
- 抽取模块
  输入：chunk 内容、标题路径、文档上下文。
  输出：候选节点、候选边、证据索引。
- 聚类模块
  输入：候选实体集合、名称规范化结果、embedding 相似度。
  输出：候选簇、候选代表、簇内归并关系。
- 对齐模块
  输入：候选簇、已有图谱、修订历史。
  输出：创建新实体、创建修订、忽略、合并等决策。
- 单元派生模块
  输入：图谱节点、图结构、局部语义相似度。
  输出：`TeachingUnit`、成员角色、命名结果。
- 课程派生模块
  输入：单元、锚点、依赖关系、历史版本。
  输出：`ThemeTreeVersion`、`PrereqDagVersion`、`CurriculumSnapshot`。

## 4. 核心设计原则

### 4.1 知识图谱是真相源

Digest 的设计中心应继续放在知识图谱上。图谱层负责表达：

- 知识点是什么
- 知识点之间是什么关系
- 这些关系来自哪些证据
- 当前内容处于什么版本

只有先建立稳定知识层，后续课程视图、问答引用、出题范围才有统一基础。

### 4.2 Teaching Unit 是教学粒度桥梁

知识节点适合表达细粒度实体，但不适合直接承担“教学编排”职责。Teaching Unit 的价值在于：

- 把多个相近知识点聚成可教单元
- 给课程结构一个稳定中间层
- 让图谱层与章节层解耦

这是 Digest 设计里最应该继续坚持的一层。

### 4.3 Theme Tree 与 Prereq DAG 不应混用

课程设计里至少存在两种关系：

- 主题归属关系
- 学习先修关系

前者适合树形表达，后者适合 DAG 表达。设计上不要试图用一棵树同时表达“是什么主题”和“应该先学什么”。

### 4.4 证据链是教学系统的可解释性基础

Digest 产出的每个节点、边、单元、课程视图，都应尽量能追溯到：

- 哪些 chunk
- 哪些文档
- 哪次构建

否则后续前端可视化、证据弹窗、人工审阅和教学解释都会失去抓手。

### 4.5 增量构建优先于整库重算

教学资料是会持续上传和更新的，因此 Digest 设计上更适合支持：

- 增量构建
- 构建任务状态
- 构建影响分析
- 版本快照

而不是每次资料变化都从零完全重建。

## 5. 设计方法

### 5.1 材料准备

Digest 的起点不是原始文件，而是材料层。理想输入应包括：

- 文档对象
- chunk 对象
- chunk embedding
- 基础元数据

这一步越标准，后面的抽取和对齐越容易稳定。

### 5.2 候选抽取

从设计上，候选抽取适合采用“结构化输出 + 证据绑定”的方法：

- 从 chunk 中抽取候选节点
- 从 chunk 中抽取候选边
- 为候选项绑定来源证据

抽取阶段的目标不是立刻得到最终真相，而是把候选集合采样得足够完整。

### 5.3 候选聚类与归并

知识资料里存在大量：

- 同名异写
- 近义表达
- 多文档重复描述

因此 Digest 需要一层候选聚类，将文本抽取结果转换为更稳定的“实体候选簇”。这一步适合结合：

- 规范化名称
- Alias
- Embedding 相似度
- LLM 辅助判断

### 5.4 实体对齐与修订

候选项进入知识层时，不应简单粗暴“同名就覆盖”。更合理的设计是：

- 先判定是否已有实体
- 再决定创建新实体还是创建新修订
- 再把证据链接挂上去

这样可以同时兼顾稳定身份和内容更新。

### 5.5 影响分析

图谱更新后，不是所有教学结构都要重算。Digest 最适合保留一层影响分析，用于判断：

- 哪些节点发生了变化
- 哪些单元受影响
- 哪些主题树挂载受影响
- 哪些先修关系需要重新推导

这层设计对增量构建非常重要。

### 5.6 Teaching Unit 派生

Teaching Unit 的生成可以理解为“教学聚类”而不是普通聚类。它要考虑的不是相似文本，而是：

- 是否适合一起讲
- 是否属于同一个局部概念组
- 是否共享证据上下文
- 是否位于同一主题

因此单元派生通常需要同时结合：

- 图结构
- 文本语义
- 课程语境

### 5.7 Theme Tree 派生

Theme Tree 的重点是“如何展示和组织”，适合表达：

- 章
- 节
- 主题
- 单元挂载

它更像课程目录，而不是知识计算图。

### 5.8 Prereq DAG 派生

Prereq DAG 的重点是“学习顺序与依赖”。它适合服务：

- 学习路径推荐
- 先修检查
- 出题顺序设计
- 薄弱点补链

设计上可以继续围绕：

- 图中依赖关系汇聚
- Teaching Unit 粒度依赖
- 环检测与消解
- 传递约简

来稳定这一层。

### 5.9 Curriculum Snapshot

课程快照层的价值在于把多种派生结果组合成一个可消费版本：

- 当前主题树
- 当前先修图
- 当前单元集合

前端和下游服务优先读快照，比直接拼装多个底层对象更稳定。

## 6. 可结合的技术方法

### 6.1 结构化抽取

Digest 非常适合继续坚持“结构化抽取而不是自由文本解析”，尤其在以下环节：

- 候选节点抽取
- 候选边抽取
- 树结构生成
- 单元命名

这种方法的优势是：

- 易校验
- 易调试
- 易存档
- 易做回归测试

### 6.2 规则 + Embedding + LLM 的混合对齐

实体对齐不适合完全依赖单一技术。更稳的路线通常是：

1. 规则快速筛掉明显同名
2. Embedding 找近似候选
3. LLM 处理边界案例

这种分层判断比“所有匹配都交给模型”更稳，也更省成本。

### 6.3 图算法

Digest 本质上是知识组织系统，因此图算法不是附属工具，而是核心能力。可持续使用和扩展的方法包括：

- 局部子图提取
- 聚类
- 影响扩散
- 环检测
- 传递约简
- 连通分量与层级分析

### 6.4 人工锚点与半自动课程编排

Theme Tree 当前已支持锚点管理，这非常适合继续演进为半自动课程编排模式：

- 系统给出结构建议
- 人工调整锚点与挂载
- 后续构建遵守人工约束

这种模式比完全自动或完全手工都更适合教学场景。

### 6.5 图谱可视化与证据弹窗

Digest 的结果天然适合可视化，不只是为了展示，更为了帮助开发与教研理解系统行为。当前前端已经有图谱、树、DAG 和证据上下文入口，这一层应继续作为 Digest 的重要输出面。

## 7. 可以继续长出的能力

Digest 后续很适合扩展以下能力：

- 节点与关系的置信度评分
- 冲突知识检测
- 多资料版本差异分析
- 图谱 diff 与课程 diff
- 单元难度估计
- 单元适学顺序打分
- 证据热力图
- 人工审核队列
- 基于单元的专题摘要
- 基于图谱的考试蓝图生成

这些能力都能直接服务 Interact、Examine 和 Profile。

---

## 8. 开发关注点

### 8.1 材料层桥接仍需继续做实

Digest 当前最重要的工程关注点之一，是保证 `Document / Chunk / Embedding` 这条材料链真正稳定存在。因为图谱抽取、RAG、证据引用都依赖它。

### 8.2 路由与生成物口径要持续核对

Digest 相关前端调用目前仍存在路径前缀漂移与旧生成物残留，因此任何 Summary 相关开发都应优先核对真实后端口径。

### 8.3 评测体系仍值得补强

Digest 的复杂度很高，后续开发时非常适合补充：

- 抽取样本集
- 对齐样本集
- 单元派生样本集
- 课程结构回归样本

否则很难判断“图谱更丰富了”还是“图谱更混乱了”。

---

## 9. 总结

Digest 是 AITeachMe 最核心的知识中枢。它负责把学习材料沉淀成可追溯、可派生、可被教学系统消费的结构化知识。

开发这层时，最重要的不是追求一次性自动化到极致，而是稳住四件事：

- 知识图谱是真相层
- Teaching Unit 是教学粒度层
- Theme Tree 与 Prereq DAG 各司其职
- 证据与版本始终可追溯

只要这四件事稳住，Digest 就会成为整个系统最有复用价值的能力中心。
