# 09. AI 技术栈与应用方法

## 1. 目标与职责
本文档用于说明 AITeachMe 当前适合采用的 AI 技术栈，以及这些技术在五大引擎中应如何使用。

重点不是简单列依赖，而是回答：

- 每类 AI 技术在项目中适合承担什么职责
- 为什么当前项目适合这种组合
- 这些技术在五大引擎里分别怎么落地
- 后续继续扩展时，应优先往哪些方向加能力

---

## 2. AI 技术使用总原则

### 2.1 先分清“规则、模型、工作流”三层

AI 系统设计时，最容易犯的错误是把所有问题都丢给大模型。更稳的做法是先分层：

- 规则层
  适合确定性强、成本敏感、容易验证的事情，例如字段校验、状态流转、客观题判分。
- 模型层
  适合语义抽取、生成、判断、改写、解释等任务。
- 工作流层
  适合多步骤、可失败、需要条件分支和状态跟踪的长流程。

AITeachMe 当前已经具备这三层的雏形，后续应继续沿这个方向细化。

### 2.2 先把输入材料做稳，再做更强的 AI

教学系统中，AI 质量很大程度由输入材料决定。没有稳定的：

- 文档材料层
- chunk 粒度
- 证据链
- 课程结构

就很难做出稳定的问答、出题和画像。

### 2.3 优先使用结构化输出

只要任务结果最终要被代码消费，就应优先考虑结构化输出，而不是自由文本后解析。这样更适合：

- 开发调试
- 失败回退
- 回归测试
- 数据落库

### 2.4 教学场景要强调可解释性

相比开放域聊天，教学场景更强调：

- 来源可回看
- 步骤可复盘
- 错因可说明
- 学习建议有依据

因此技术选型不应只看模型能力，还要看是否便于保留证据和状态。

---

## 3. 当前适合采用的核心技术栈

| 技术 | 当前用途 | 适合承担的角色 |
| --- | --- | --- |
| LiteLLM | 统一文本、流式、Embedding 调用 | 模型接入层 |
| Instructor + Pydantic | 结构化输出 | 抽取、生成、判定约束层 |
| LangGraph | 状态机工作流 | 长流程编排层 |
| sqlite-vec | 本地向量检索 | RAG 与语义近邻层 |
| Jinja2 Prompt Loader | Prompt 模板化 | Prompt 工程层 |
| MarkItDown / PyMuPDF4LLM / PyMuPDF | 文档解析 | 材料接入层 |
| React Query | 前端异步状态 | 页面数据访问层 |
| Orval | OpenAPI 生成 | 前端 client 生成层 |
| MSW | 本地 mock | 联调模拟层 |

这套组合的特点是：

- 本地优先
- 工程复杂度可控
- 适合资料驱动型教学系统
- 便于逐步增强，而不必一次引入重量级基础设施

---

## 4. LiteLLM：模型接入层

### 4.1 适用价值

LiteLLM 的价值不在于“换模型方便”这么简单，更重要的是它能把：

- 文本补全
- 流式补全
- Embedding

统一到一套调用风格里。

### 4.2 在本项目中的适合用法

当前项目最适合把 LiteLLM 放在 `shared/infra/llm_support` 层，继续承担：

- 统一超时控制
- 重试
- 异常包装
- 模型名与 base URL 配置

这样业务层和 Agent 层不需要关心供应商细节。

### 4.3 后续可以继续加的能力

LiteLLM 层后续很适合继续加入：

- 按引擎拆分模型配置
- token / cost 统计
- 延迟日志
- provider fallback
- 按任务类型切模型

对于 AITeachMe 这种五大引擎并存的系统，这类模型路由能力会越来越重要。

---

## 5. Instructor + Pydantic：结构化输出层

### 5.1 为什么非常适合本项目

AITeachMe 有大量任务不是“给用户看一段自然语言”就结束，而是要把结果继续喂给程序，例如：

- 候选知识节点
- 候选边
- 单元命名
- 课程结构
- 试卷题目
- 判卷结果

这些任务天然适合用 `Instructor + Pydantic` 约束结构。

### 5.2 适合落地的任务类型

当前最适合继续采用结构化输出的场景包括：

- Digest 抽取
- Examine 出题
- Examine 主观题分步骤评分
- Profile 报告结构化建议
- Interact 中的意图分类或学习策略选择

### 5.3 设计建议

使用结构化输出时，建议注意：

- schema 字段尽量少而稳
- 先抽核心字段，再考虑花哨字段
- 字段含义尽量能直接落库或直接渲染
- 允许有兜底字段，但不要让兜底字段吞掉主要结构

### 5.4 非常适合继续加入的做法

- schema 版本号
- 结构化输出样例集
- 失败重试策略
- 宽松模式与严格模式
- 输出质量校验器

---

## 6. LangGraph：工作流层

### 6.1 为什么适合 AITeachMe

只要流程具有以下特征，就很适合用显式工作流表达：

- 多步骤
- 步骤间有中间状态
- 可能失败
- 需要条件分支
- 需要记录当前进行到哪一步

Digest 正好完全符合这个特征，因此当前 LangGraph 首先落在 Digest 是很自然的选择。

### 6.2 当前最适合使用 LangGraph 的场景

- 图谱构建
- 课程视图派生

后续如果继续扩展，也很适合考虑：

- 大型试卷生成
- 批量主观题评分
- 多阶段学习报告
- 人工审核插入点

### 6.3 工作流设计建议

LangGraph 在本项目里最适合配合这些设计：

- 显式状态对象
- 明确的失败分支
- 步骤级日志
- job 表与工作流状态同步
- 可在中间插入人工校验

这能让复杂 AI 流程不再是难以调试的黑盒。

---

## 7. sqlite-vec：检索层

### 7.1 为什么适合当前阶段

对于本地优先项目，sqlite-vec 的优势非常明显：

- 部署简单
- 本地开发方便
- 不需要额外向量数据库
- 和 SQLite 主库容易协同

对 AITeachMe 这种中等规模学科资料场景，它是一个非常实用的底座。

### 7.2 适合承担的角色

当前 sqlite-vec 主要适合服务：

- Chat 的 chunk 检索
- Digest 中的语义相似度辅助
- 单元聚类或主题挂载的相似度计算

### 7.3 设计注意点

向量检索真正稳定的关键，不只在向量库，而在：

- chunk 切分是否合理
- chunk 是否带标题路径
- embedding 模型是否稳定
- 是否保留来源信息
- top-k 与阈值是否贴合教学场景

### 7.4 适合继续叠加的技术

后续很适合在 sqlite-vec 上叠加：

- SQLite FTS5 关键词检索
- 混合召回
- rerank
- context compression
- selected context 优先策略

对教学资料来说，混合检索通常比纯向量更稳。

---

## 8. 文档解析技术：材料接入层

### 8.1 当前组合为什么合理

教学资料常见格式非常杂，当前项目使用：

- `MarkItDown`
- `PyMuPDF4LLM`
- `PyMuPDF`

这类多解析器组合是合理的，因为不同格式和不同质量的 PDF / 文档往往需要不同工具链。

### 8.2 后续可以继续增强的方向

在材料解析层，后续很适合继续考虑：

- OCR
- 视觉语言模型
- 表格结构恢复
- 公式识别
- 版面分析
- source map 生成

这些能力对教学资料特别重要，因为教材、课件和讲义里图文混排非常常见。

### 8.3 设计建议

解析层最适合的长期策略不是更换单一大工具，而是：

- 先做路由
- 再做回退
- 再做质量选择

这样能显著提高整体稳定性。

---

## 9. Prompt 工程：提示词层

### 9.1 为什么必须模板化

对于多引擎系统，Prompt 如果散落在业务逻辑中，很快就会失控。当前项目已经有：

- Prompt 模板
- Jinja2 填充
- 严格变量校验

这是一条非常适合继续坚持的路线。

### 9.2 本项目中适合的 Prompt 组织方式

建议按引擎与任务拆分 Prompt，例如：

- Ingest 视觉解析 Prompt
- Digest 抽取 / 对齐 / 命名 Prompt
- Interact 讲解 / 引导 / 复盘 Prompt
- Examine 出题 / 判卷 / 错因 Prompt
- Profile 建议生成 Prompt

### 9.3 适合继续加入的能力

- Prompt 版本号
- few-shot 样例
- 输出约束注释
- Prompt 回归样本
- Prompt 成本与失败率统计

这会让 Prompt 从“经验文本”升级为“可维护资产”。

---

## 10. AI 评测与观测

### 10.1 为什么必须单独设计评测层

AI 功能很容易出现“代码没报错，但结果已经明显变差”的情况，因此项目后续非常适合补强评测层。

### 10.2 适合优先建设的评测类型

- Digest 抽取样本集
- Interact 问答样本集
- Examine 出题与判卷样本集
- Profile 报告样本集

### 10.3 适合记录的观测信息

- 模型名
- 请求耗时
- 重试次数
- token 与成本
- 结构化输出失败率
- SSE 中断率
- 关键任务成功率

这些指标对 AI 系统远比一般 CRUD 系统重要。

---

## 11. 五大引擎的技术应用建议

| 引擎 | 优先技术 | 重点方法 |
| --- | --- | --- |
| Ingest | 多解析器、OCR、source map、质量评估 | 先稳定材料，再交给下游 |
| Digest | 结构化抽取、Embedding 对齐、LangGraph、图算法 | 图谱真相层 + Teaching Unit + 课程派生 |
| Interact | RAG、混合检索、Prompt 模式化、SSE | 教学对话而非泛聊天 |
| Examine | 结构化出题、规则判卷、LLM 评分、错因分类 | 诊断测评而非题库堆砌 |
| Profile | 统计画像、事件流、时间衰减、报告生成 | 学习状态层而非报表层 |

这张表可以作为后续选技术时的快速参考。

---

## 12. 当前项目最值得优先做实的 AI 方向

结合现有代码，当前最值得优先做实的不是“再接更多模型”，而是：

- 把材料层与 chunk 层做稳
- 把结构化输出与 schema 体系做稳
- 把检索与来源链做稳
- 把工作流状态和任务对象做稳
- 把评测与日志做稳

只有这几个底座稳了，后续不管是更强的图谱、更强的对话还是更强的测评，都会更容易长期维护。

---

## 13. 总结

AITeachMe 当前最适合的 AI 路线，不是追求“大而全 Agent”，而是围绕教学闭环，把几类关键技术组合好：

- LiteLLM 统一模型接入
- Instructor + Pydantic 约束结构化输出
- LangGraph 编排长流程
- sqlite-vec 支撑本地检索
- 多解析器构建稳定材料层
- Prompt 模板化提升可维护性

这条路线的优势是务实、可落地、适合本地优先架构，也非常适合继续围绕五大引擎逐步长出更强的教学能力。
