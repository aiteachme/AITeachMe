# 02. 领域模型与状态

## 1. 目标与职责
本文档用于说明系统中的核心对象、对象关系和关键状态，重点回答：

- 系统里真正重要的领域对象有哪些
- 这些对象是“身份对象”还是“派生对象”
- 哪些状态属于知识层，哪些状态属于学习者层

---

## 2. 领域分层

当前领域模型可以分为四组：

| 分层 | 主要对象 | 作用 |
| --- | --- | --- |
| 工作空间与资料层 | `Subject`、`RawFile`、`Document`、`DocumentChunk` | 管理学科、原始资料和可处理材料 |
| 知识与课程层 | `KnowledgeNode`、`KnowledgeEdge`、`KnowledgeRevision`、`TeachingUnit`、`ThemeTreeVersion`、`PrereqDagVersion`、`CurriculumSnapshot` | 管理知识结构与教学视图 |
| 互动与测评层 | `ChatMessage`、`Exam`、`Question`、`ExamSubmission`、`AnswerRecord`、`Mistake` | 管理学习过程中的对话与测评行为 |
| 画像层 | `UserProfile` | 管理掌握度、薄弱点、报告输入状态 |

这种分层设计的核心价值是把“知识世界”和“学习者世界”分开：

- 知识世界回答“这个学科里有什么”
- 学习者世界回答“这个人现在学到了什么”

---

## 3. 核心对象

### 3.1 Subject

`Subject` 是顶层工作空间对象，承担三个角色：

- 数据隔离边界
- 前后端路由边界
- 本地存储目录边界

设计上应继续把学科视为一等实体，而不是简单的字符串标签。

### 3.2 RawFile

`RawFile` 是资料接入层的核心对象，表示用户上传的原始材料。它当前承载：

- 文件身份
- 文件类型
- 文件路径
- 解析状态
- 解析产物位置
- 一部分质量与分类元信息

`RawFile` 的重点不是“知识内容”，而是“材料接入过程”。

### 3.3 Document 与 DocumentChunk

这两个对象应当被视为“知识处理材料层”：

- `Document` 表示某份可处理文档
- `DocumentChunk` 表示检索、抽取、证据引用的最小处理单元

设计上，后续所有 RAG、图谱抽取、证据溯源都应尽量围绕这一层展开，而不是直接把 `RawFile` 当作知识处理对象。

### 3.4 KnowledgeNode / KnowledgeEdge / Revision

知识图谱层当前采用“身份 + 修订”的设计方式：

- `KnowledgeNode` / `KnowledgeEdge`
  表达实体与关系的稳定身份
- `KnowledgeRevision` / `EdgeRevision`
  表达当前内容版本、摘要、描述等可变信息

这种设计的意义是：

- 允许知识实体长期存在
- 允许内容随着资料更新而演进
- 为证据链接、版本比较和增量构建留出空间

### 3.5 TeachingUnit

`TeachingUnit` 是当前设计里非常关键的桥梁对象。它不直接等于“知识节点”，也不直接等于“课程章节”，而是：

- 一组可教学、可组合、可安排先后的知识单元

从设计上看，它是图谱层与课程视图层之间最适合长期稳定存在的中间粒度。

### 3.6 ThemeTree / PrereqDag / CurriculumSnapshot

这三类对象分别承担不同职责：

- `ThemeTreeVersion`
  表达面向教学展示的主题树
- `PrereqDagVersion`
  表达面向学习顺序的先修依赖图
- `CurriculumSnapshot`
  表达一次可发布、可读取的课程快照

设计上应避免把“章节包含关系”和“先修关系”强行塞进同一棵树。

### 3.7 Chat / Exam / Profile

这一组对象属于学习者状态层：

- `ChatMessage`
  记录教学对话过程
- `Exam` / `Question` / `ExamSubmission` / `AnswerRecord` / `Mistake`
  记录测评过程和错题结果
- `UserProfile`
  记录掌握度与学习状态

这组对象不应直接污染知识结构对象。

---

## 4. 关键关系

当前系统中的关键关系可以概括为：

`Subject -> RawFile -> Document -> DocumentChunk -> KnowledgeNode / KnowledgeEdge -> TeachingUnit -> ThemeTree / PrereqDag -> Chat / Exam -> UserProfile`

这条链路表达了两个重要原则：

- 上游负责提供更稳定的知识基础
- 下游负责消费这些基础并产生学习状态

---

## 5. 状态设计

### 5.1 资料处理状态

`RawFile` 当前是最明显的状态对象之一。设计上应区分：

- 上传成功
- 等待解析
- 解析处理中
- 解析完成
- 解析失败

除此之外，还可以继续扩展：

- 质量评估状态
- 去重状态
- 人工确认状态

### 5.2 知识构建状态

Digest 相关对象中，`GraphDigestJob` 和 `CurriculumDeriveJob` 表达了显式工作流状态。设计上这类对象应继续承担：

- 当前步骤
- 总体状态
- 错误信息
- 时间戳

它们不只是“任务表”，也是知识构建过程可观测性的基础。

### 5.3 课程发布状态

`ThemeTreeVersion`、`PrereqDagVersion`、`CurriculumSnapshot` 属于版本状态对象，强调：

- 草稿构建
- 当前可读版本
- 历史版本留存

这使课程结构可以长期演进，而不需要每次重建都覆盖旧结果。

### 5.4 学习过程状态

聊天、考试、画像虽然没有统一的状态机表述，但设计上仍然可以分成：

- 对话进行中 / 已完成
- 试卷已生成 / 已提交 / 已复盘
- 画像最近更新 / 长期趋势 / 错题积累

这部分状态后续适合进一步显式化。

---

## 6. 建模原则

### 6.1 身份与内容分离

如果一个对象需要长期被引用、被关联、被追踪，就应优先拥有稳定身份；如果一个对象主要承载描述、摘要、文本内容，则应考虑与身份分开。

### 6.2 知识状态与学习者状态分离

知识图谱、课程结构描述“知识本身”；聊天、考试、画像描述“学习者与知识的交互结果”。二者应该通过稳定锚点连接，而不应直接混在一起。

### 6.3 派生视图不直接充当真相源

Theme Tree、Prereq DAG、Curriculum Snapshot 都是派生视图。设计上应该允许它们服务展示和教学，但不要反向替代图谱层的知识真相源角色。

### 6.4 证据链必须可追溯

只要对象是由资料抽取、归纳、推断得到的，就应尽可能保留：

- 来自哪个 chunk
- 来自哪个文档
- 来自哪次构建

这是后续做解释、调试和人工修订的前提。

### 6.5 画像锚点应逐步稳定化

当前画像主要以 `knowledge_point` 字符串为锚点，这对 MVP 足够，但长期设计上更适合逐步迁移到：

- `knowledge_node_id`
- `teaching_unit_id`

这样可以减少命名变化带来的状态漂移。

---

## 7. 存储设计

### 7.1 SQLite

当前 SQLite 负责保存：

- 核心业务表
- 图谱与课程表
- 聊天、考试、画像表

它适合当前本地优先架构，但也要求表结构和状态语义尽量清晰。

### 7.2 sqlite-vec

向量表 `chunk_embeddings` 是当前检索层的重要组成部分。设计上它应与 `DocumentChunk` 保持稳定一一映射关系，而不是独立漂浮存在。

### 7.3 本地文件系统

本地文件系统当前承担：

- 原始文件存储
- Markdown 产物存储
- 图片与附件资源存储

因此领域建模上不能忽视文件路径和资产目录，它们仍是重要的一部分状态。

---

## 8. 开发关注点

### 8.1 Document / Chunk 材料层仍需持续收紧

从设计上，`Document` 和 `DocumentChunk` 应该是 Ingest、Digest、Interact 三者共享的桥接层。当前代码里这条桥还不够稳，因此开发时应优先确保这层的一致性。

### 8.2 画像仍主要使用字符串锚点

`UserProfile` 目前用 `knowledge_point` 字符串记录掌握度，这使实现简单，但也意味着后续知识点命名变化会带来画像同步问题。

### 8.3 学习行为事件层还比较薄

当前 `UserProfile` 主要由考试结果回流得到。设计上后续更理想的方式是逐步引入更明确的学习事件层，让画像不仅能消费考试，也能消费聊天、复练、单元学习等行为。

---

## 9. 总结

AITeachMe 的领域模型已经具备较好的骨架：

- `Subject` 管工作空间
- `RawFile / Document / Chunk` 管材料
- 图谱与 Teaching Unit 管知识和教学粒度
- Chat / Exam / Profile 管学习者状态

后续开发时，最重要的不是继续增加对象种类，而是让这些对象的边界、关系和状态更加稳定、可追踪、可复用。
