## 十一、待确认问题

> 原则：只保留真正会影响实现路径的问题，其余默认按推荐方案执行。
> 最后更新：2026-04-09

---

## 11.1 可以直接按推荐方案执行的默认决策

如果你没有额外推翻，建议默认按下面执行：

| 主题 | 推荐默认 |
| --- | --- |
| 课程模式 | 考试 / 冲刺类请求默认 `sprint`；学科 / 系统学习类请求默认 `systematic` |
| 文风 | `sprint -> casual`，`systematic -> professional` |
| 系统课字数 | 默认目标 10000-15000 字 |
| 检索策略 | 优先本地资料，其次教育语料和教育 Web，最后通用 Web |
| 教学能力落位 | `shared/infra` 做通用能力，`teaching` 做教学语义 |
| canonical memory | `app.shared.infra.memory` |

## 11.2 仍需你拍板的关键问题

### 1. 图像生成供应商

影响范围：

- `ImageGenerator` 的真实落地方案
- 资产存储和成本控制

推荐默认：

- MVP 用 DashScope / 通义体系
- 后续再评估 DALL-E / Gemini 等

### 2. 速成课章节数量要不要硬锁死

当前建议：

- 不建议永远锁死 4 章
- 更建议“4-6 章 + 每章固定教学区块”

原因：

- 主题大小差异很大
- 过死的章数约束容易牺牲内容质量

### 3. 系统课是否对用户开放“精简版”

当前建议：

- 默认坚持 10000+ 字
- 仅在用户明确要求时，允许“系统课精简版”

### 4. 本地教育语料库的首批范围

当前建议：

- 第一批只做高数、线代、概率论
- 先把“做深”跑通，再横向扩学科

### 5. 商业资料的合规策略

当前建议：

- 不把商业资料原文沉淀进系统长期语料库
- 只允许用户上传后在当前 subject 构建内使用
- 系统长期语料只存授权明确或自建衍生条目

### 6. 交互 HTML 的优先级

当前建议：

- 不进入第一阶段主链路
- 先把文字、公式、Mermaid、图片做好
- 交互 HTML 作为 Phase 5 之后增强项

### 7. `teaching/memory` 的最终命运

当前建议：

- 现在保留兼容 facade
- 后续逐步清理
- 不再新增底层存储逻辑

如果你希望保留它，也必须把它限定为“教学友好包装层”，而不是第二套真相源。

## 11.3 需要持续验证但不需要现在停下来问的问题

这些问题不阻塞当前文档和架构设计，可以边做边验证：

- `purify` 步骤是否真的带来足够质量收益
- `sprint` / `systematic` 的默认 retrieval profile 是否需要再细分
- 哪些教学块最能提高用户留存与复习效率
- 图片和 Mermaid 的实际前端呈现效果
- 系统课在不同学科上的合理字数区间

## 11.4 一句话结论

真正需要你明确拍板的，其实只剩少数产品和策略问题。
架构方向本身已经可以定下来，不需要因为一些次级细节继续拖延主线重构。
