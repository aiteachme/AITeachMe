# 03. 接口设计规范与联调流程

## 1. 目标与职责
本文档定义 AITeachMe 当前阶段的接口设计规范，重点包括：

- 路由和资源应该如何组织
- 请求、响应、分页、错误、流式接口如何统一
- 长流程接口应采用什么模式
- OpenAPI、前端调用、MSW 应如何保持一致

---

## 2. 真相源与边界

### 2.1 接口真相源

当前项目的接口真相源是后端源码：

- `backend/app/api/*`
- `backend/app/schemas/*`

以下内容都只能视为派生产物或联调辅助材料：

- `frontend/openapi.json`
- `frontend/src/api/generated/*`
- `frontend/src/mocks/*`
- `backend/docs/manual-testing.md`

### 2.2 接口文档的职责边界

本篇文档主要负责“设计规范”。具体业务设计放在各引擎文档中，具体代码细节以源码为准。

---

## 3. 资源分组规范

当前项目已经形成一套比较稳定的资源分组，应继续保持：

- `health`
- `system`
- `auth`
- `subjects`
- `files`
- `knowledge`
- `chats`
- `exams`
- `profile`

这套分组的含义是：

- 先按领域资源分组
- 再在资源下组织动作
- 避免按前端页面临时拼装零散接口

---

## 4. 路径与命名规范

### 4.1 顶层路径规范

当前统一采用：

`/api/v1/subjects/{subject}/{resource}/...`

其设计意义是：

- `/api/v1`
  明确服务版本前缀
- `subjects/{subject}`
  明确学科是顶层工作空间
- `{resource}`
  明确资源分组边界

### 4.2 资源命名规范

当前建议继续使用复数资源名作为集合边界：

- `files`
- `chats`
- `exams`

`knowledge` 和 `profile` 虽然不是严格复数，但已经形成稳定资源组语义，当前不建议随意变动。

### 4.3 动作子路径规范

在当前开发阶段，允许使用显式动作子路径，例如：

- `/upload`
- `/parse`
- `/status`
- `/send`
- `/make`
- `/submit`
- `/list`
- `/clear`

适用场景包括：

- 业务动作强于纯 REST 语义
- 需要快速收敛前后端
- 一个资源下存在多种任务型操作

后续即使接口语义进一步细化，也应优先保持资源边界稳定，再考虑动作命名是否调整。

---

## 5. 方法设计规范

### 5.1 当前阶段统一以 POST 为主

当前业务接口应继续保持“绝大多数使用 `POST`”的设计规则，仅健康检查一类简单读取保留 `GET`。

这样做的好处是：

- 前后端联调成本低
- 请求体表达能力强
- 更适合复杂查询和任务触发
- 方便在开发早期快速演进字段

当前例外是：

- `GET /api/health`

### 5.2 什么时候可以细化方法语义

后续如果某类资源已经满足以下条件，可以再逐步细化为 `GET` / `DELETE` / `PUT`：

- 资源边界长期稳定
- 请求参数简单
- OpenAPI 与前端生成链路稳定
- 不再频繁调整 body 结构

在当前阶段，不应把“方法语义优雅”放在“协作效率”前面。

---

## 6. 请求体设计规范

### 6.1 请求体统一使用对象

即使只有一个字段，也建议使用对象 body，而不是直接发送裸值。这样可以保证：

- 结构稳定
- 未来可扩展
- OpenAPI 生成更一致

### 6.2 分页请求规范

分页请求统一采用 body 传递：

- `page`
- `size`

如果需要过滤条件，也统一放在 body 中，不建议早期把一部分字段塞 query，一部分字段塞 body。

### 6.3 批量请求规范

批量动作优先使用数组字段表达，例如：

- `file_ids`
- `answers`

不要通过多次重复调用单对象接口替代真正的批量请求。

### 6.4 长流程触发请求规范

长流程触发请求可带：

- 目标对象 ID 列表
- `idempotency_key`
- 可选配置项

这样既方便防重，也方便未来把执行器从 `BackgroundTasks` 升级为队列系统。

---

## 7. 响应设计规范

### 7.1 统一响应包裹

当前项目统一使用：

- `ApiResponse[T]`
- `PaginatedData[T]`

建议继续保持这一规范。

成功响应建议保持：

- `code`
- `message`
- `data`

其中真正业务内容放在 `data` 中。

### 7.2 分页响应规范

分页接口统一返回：

- `items`
- `total`
- `page`
- `size`

如果当前个别接口尚未把 `page/size` 回传完整，设计上仍建议统一到这一形态。

### 7.3 错误响应规范

错误响应应由统一异常处理器输出，至少保持：

- 统一状态码
- 统一 `code/message/data`
- 统一业务异常到 HTTP 状态的映射

不要在不同资源组中手写彼此不一致的错误格式。

---

## 8. 流式接口规范

### 8.1 适用场景

当前流式接口主要适用于教学对话：

- 用户需要边生成边阅读
- 前端需要逐 token 渲染
- 服务端希望返回引用上下文与完成事件

### 8.2 当前设计方式

当前采用：

- `POST` 发送请求
- `text/event-stream` 返回响应

这是当前阶段适合保留的方案。

### 8.3 SSE 事件设计建议

建议流式接口统一使用三类事件语义：

- `token`
  增量文本
- `done`
  结束事件，附带结构化元信息
- `error`
  流中错误

`done` 事件适合承载：

- `turn_id`
- `contexts`
- 其他最终元数据

这样前端可以在流结束后一次性完成记录入库、来源展示和状态切换。

---

## 9. 长流程接口规范

### 9.1 统一模式

对文件解析、知识构建这类耗时流程，设计上应统一采用：

1. 触发接口
2. 状态查询接口
3. 后台执行器

这是当前项目最应坚持的一条接口模式。

### 9.2 状态对象要求

长流程状态对象至少应包含：

- `job_id`
- `status`
- `current_step`
- `error_message`
- `created_at / updated_at`

这样前端才能做稳定轮询，后端才能做可靠监控。

### 9.3 幂等与锁

长流程应优先考虑：

- `idempotency_key`
- 学科级构建锁
- 相同请求复用已有任务

这类设计不一定一次做全，但接口语义应为此预留空间。

---

## 10. OpenAPI、Orval、MSW 同步规范

### 10.1 建议的同步链路

当前推荐的单一同步链路为：

1. 修改后端路由与 schema
2. 启动后端服务
3. 运行 `backend/scripts/export_api_docs.py`
4. 刷新 `frontend/openapi.json`
5. 运行 Orval 重新生成前端 client
6. 同步手写 API 调用
7. 同步 MSW mock

### 10.2 设计原则

- 先改真相源，再改生成物
- 先改 OpenAPI，再改前端调用
- mock 应服务真实接口，而不是反过来塑造接口

### 10.3 当前前端的现实情况

当前前端同时存在：

- 手写 `axios` 调用
- Orval 生成代码
- MSW mock

因此在任何接口变更前，必须先确认页面实际调用的是哪一套。

---

## 11. 当前项目的已落地口径

### 11.1 当前真实资源组

当前后端真实资源组为：

- `files`
- `knowledge`
- `chats`
- `exams`
- `profile`

### 11.2 当前需要明确记录的口径漂移

当前项目已确认存在以下问题：

- `ChatPage` 和 MSW 仍有旧 `/chat/*` 调用
- `ExamPage` 和 MSW 仍有旧 `/exam/*` 调用
- `frontend/openapi.json` 不是最新后端真相
- `frontend/src/api/generated/*` 仍有旧接口形态
- `frontend/src/api/graphApi.ts` 部分路径缺少 `/knowledge` 前缀
- `knowledge_clear` 当前在后端代码中的路径实际为 `/knowledge/knowledge/clear`

这些问题都应在开发时显式核对，不能默认前端生成物是正确的。

---

## 12. 接口评审清单

每次新增或修改接口时，建议至少检查以下问题：

- 是否放在正确的资源组下
- 是否仍以 `Subject` 作为顶层边界
- 是否保持了当前阶段的 `POST` 设计约定
- 请求体是否是可扩展对象
- 响应是否使用统一包裹
- 是否需要分页结构
- 是否属于长流程，需要触发与状态分离
- 是否需要流式返回
- OpenAPI、手写调用、MSW 是否会同步更新

---

## 13. 总结

AITeachMe 当前阶段的接口设计重点，不是追求形式上的 REST 完美，而是建立一套稳定、统一、可持续迭代的工程规范：

- 路由按资源分组
- 业务接口以 `POST` 为主
- 响应统一包裹
- 长流程统一任务模式
- 流式接口统一 `POST + SSE`
- 后端源码作为唯一真相源

只要这几条被持续遵守，前后端协作和后续代码演进就会稳定很多。
