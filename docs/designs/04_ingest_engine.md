# 04. Ingest 引擎

## 1. 目标与职责
Ingest 引擎负责把用户提交的原始资料转成后续系统可稳定消费的学习材料。

它解决的不是“理解知识”本身，而是知识处理之前的基础工程问题：

- 接收多种格式资料
- 判断资料类型与处理方式
- 选择合适解析器
- 输出规范化 Markdown
- 提取图片、表格、附件等资产
- 为后续图谱、检索、证据引用提供统一材料层

如果说 Digest 决定“知识如何组织”，那么 Ingest 决定“知识材料能否被可靠组织”。

---

## 2. 当前实现落点

当前代码里，Ingest 主要落在以下位置：

- 前端页面：`frontend/src/pages/UploadPage.tsx`
- 后端资源组：`files`
- 业务编排：`backend/app/services/file_service.py`
- 解析与规范化：`backend/app/agents/ingest/*`
- 关键模型：`RawFile`

这说明当前项目已经把资料接入单独建成了一层，而不是把“上传文件”塞进任意一个通用接口里。

## 3. Pipeline 设计

### 3.1 接入与解析主 Pipeline

| 步骤 | 子模块 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1. 文件接入 | `UploadPage` + `save_uploaded_files` | `subject`、上传文件列表 | 本地文件、`RawFile` 记录 |
| 2. 解析触发 | `request_files_parse` | `file_ids`、当前 `RawFile` 状态 | 进入 `processing` 的文件集合 |
| 3. 后台分发 | `run_parse_files_background` | `subject`、待处理文件 ID 列表 | 单文件解析任务调度 |
| 4. 轻量分类 | `classifier.classify_file` | 文件路径、文件类型 | 文件类别、推荐解析链、语言、页数估计 |
| 5. 解析路由 | `orchestrator.parse_file` | 文件路径、资产目录、分类结果 | 原始 Markdown、提取出的图片/附件 |
| 6. 规范化 | `canonicalizer.canonicalize_markdown` | 原始 Markdown | 规范化 Markdown |
| 7. 结果落盘 | `file_service._parse_one_file` | 规范化 Markdown、资产目录、分类结果 | `markdown_path`、`asset_dir`、完成状态、解析元数据 |
| 8. 下游桥接 | 材料化层 | `markdown_path`、原始文件元信息 | `Document`、`DocumentChunk`、向量、source map |

当前代码里，1 到 7 已基本存在；第 8 步是整个 Ingest 设计里最值得继续做实的桥接层。

### 3.2 关键子模块输入输出

- 接入模块
  输入：浏览器上传的原始文件、学科标识。
  输出：本地文件路径、`RawFile` 持久化记录、待解析状态。
- 分类模块
  输入：文件路径、扩展名、文件内容特征。
  输出：文件类别、推荐解析器、语言、页数和基础质量线索。
- 解析模块
  输入：文件路径、资产目录、具体解析器选择。
  输出：原始 Markdown、图片与附件资源。
- 规范化模块
  输入：原始 Markdown。
  输出：标题层级统一、块结构更稳定的 Markdown。
- 持久化模块
  输入：Markdown、资产目录、分类信息、耗时统计。
  输出：更新后的 `RawFile`、解析元数据、后续可供 Digest 消费的材料。
- 材料化模块
  输入：规范化 Markdown、来源位置、原始文件元信息。
  输出：`Document`、`DocumentChunk`、embedding、source map。

## 4. 核心设计原则

### 4.1 资料接入优先追求稳定，而不是一步到位智能化

Ingest 首先要解决的是“把资料稳定转成可用材料”，而不是一上来就追求高度语义理解。设计上应坚持先把以下事情做好：

- 文件接收可靠
- 解析结果稳定
- 输出格式统一
- 附件关系可追踪
- 异常结果可重试

### 4.2 解析器应按材料类型路由

不同资料格式差异很大，不适合追求单一“万能解析器”。更合理的做法是建立解析器路由层，根据：

- PDF
- DOCX
- PPTX
- 图片

选择不同能力组合，再在结果层统一为标准 Markdown。

### 4.3 规范化材料层必须独立存在

原始文件和知识图谱之间需要一个稳定中间层。设计上建议持续强化：

- `RawFile`
- `Document`
- `DocumentChunk`

这条材料链路，让后续检索、图谱、证据、课程派生都围绕同一套材料工作，而不是各自重新理解原始文件。

### 4.4 资产与来源必须可追溯

教学系统中的图片、公式、表格、图示往往和正文同样重要。Ingest 不应只产出文本，还应尽可能保留：

- 资产目录
- 原始图片
- 页码或位置线索
- 段落与块级来源关系

这样后续才能做证据弹窗、图文引用、选段问答和人工核验。

### 4.5 Ingest 与 Digest 职责要清晰分离

Ingest 负责把资料变成可处理材料；Digest 负责把材料组织成知识结构。不要把抽取、聚类、知识归纳提前塞到 Ingest 中，否则整个链路会变得不可控。

## 5. 设计方法

### 5.1 接入阶段

接入阶段的重点不是业务语义，而是材料元信息。建议持续保留并扩展以下字段：

- 文件名
- 文件类型
- 文件路径
- 文件大小
- 内容哈希
- 估计页数
- 语言识别结果
- 分类结果

这样一来，后续可以支持：

- 重复文件检测
- 大文件限流
- 解析策略切换
- 多语言提示词选择

### 5.2 分类阶段

分类的目标不只是识别 MIME type，而是判断该文件更适合哪种处理模式。例如：

- 文本密集型 PDF
- 扫描型 PDF
- 图像主导型课件
- 结构化文档
- 演示文稿

这种轻量分类会直接影响解析策略、OCR 需求、图片处理方式和质量评估标准。

### 5.3 解析阶段

解析阶段建议分成三层：

1. 原始文本抽取
2. 版面与结构修正
3. 统一格式输出

当前项目里已经具备多种解析能力，后续设计上可以继续保持“多路解析 + 统一出口”的模式。

### 5.4 规范化阶段

统一 Markdown 不是为了“好看”，而是为了后续可处理。规范化时建议重点处理：

- 标题层级
- 段落切分
- 列表格式
- 图片占位与引用
- 表格表示
- 冗余空白与噪声文本

这一步做得越稳，后续 chunking、抽取、检索越稳。

### 5.5 材料化阶段

Ingest 的终点不应该只是得到一个 Markdown 文件，而应该是得到一套可复用的材料对象：

- 文档对象
- 块级对象
- 资产对象
- 来源映射

这套材料层是后续所有 AI 模块共享的输入基础。

### 5.6 质量控制阶段

Ingest 设计上应尽量具备轻量质量评估能力，例如：

- 文本覆盖率
- 图片数量
- 乱码比例
- 标题结构完整度
- 识别失败段落比例

这些指标既可以服务前端提示，也可以服务自动重试或人工确认。

## 6. 可结合的技术方法

### 6.1 当前已适合继续使用的技术

当前项目已具备较好的基础组合：

- `MarkItDown`
- `PyMuPDF4LLM`
- `PyMuPDF`
- 图片解析链路
- Markdown 规范化

这套组合适合继续作为本地优先方案的主干。

### 6.2 OCR 与视觉解析

对于扫描件、课件截图、白板图、图像型资料，可以结合：

- OCR 引擎
- 视觉语言模型
- 版面分析模型

适合的场景包括：

- 扫描型 PDF
- 图片型课件
- 公式图像
- 表格截图

设计上应把 OCR / VLM 视作 Ingest 的可选增强层，而不是默认每个文件都走重型视觉链路。

### 6.3 表格与公式恢复

教学资料中大量内容会以表格和公式出现，后续可继续结合：

- 表格结构恢复
- LaTeX / MathML 转换
- 公式图片识别
- 单元格语义保留

这类能力会直接提升后续 Digest 的知识抽取质量。

### 6.4 多解析器投票与回退

如果某一类材料解析结果不稳定，可以采用：

- 主解析器
- 回退解析器
- 质量评分选择

例如对 PDF 同时尝试两种方式，再按质量指标选择更优结果。

### 6.5 Source Map

对教学系统来说，后续非常值得建设的一层是 source map，即记录：

- Markdown 段落来自哪一页
- 某个 chunk 来自哪一段原文
- 某张图来自哪个文件位置

一旦这层建立起来，证据引用和交互式问答的解释性会明显提升。

---

## 7. 可以继续长出的能力

Ingest 后续很适合继续扩展下面这些能力：

- 重复资料自动检测
- 同一学科多资料版本对齐
- 章节目录自动抽取
- 文档质量评分与排序
- 图文块混合 chunk
- 讲义 / 题库 / 课件的不同解析模板
- 双语资料识别与语言分流
- 特殊题型资料的结构化预处理

这些能力都属于“让材料更适合被教学系统消费”，因此应被视为 Ingest 的自然延展。

---

## 8. 开发关注点

### 8.1 当前主链路仍主要停在 RawFile 与 Markdown

当前项目已经能把文件解析为 Markdown 并记录到 `RawFile`，但从设计目标看，还需要进一步把材料稳定桥接到：

- `Document`
- `DocumentChunk`
- `chunk_embeddings`

这是 Ingest 和 Digest / Interact 之间最值得持续收紧的连接点。

### 8.2 当前任务执行器仍是进程内后台任务

设计上文件解析已经具备“触发 + 状态查询”的雏形，但执行器仍是 `BackgroundTasks`。因此接口语义要尽量设计得独立于执行器本身。

### 8.3 当前质量层还比较轻

虽然已经有部分分类和质量字段，但“质量控制”还没有真正成为 Ingest 的完整设计层。后续只要继续增强 Ingest，优先级最高的方向之一就是质量与来源。

---

## 9. 总结

Ingest 引擎的价值，不在于把文件“上传进来”，而在于把混乱资料变成后续所有引擎都能稳定消费的统一材料层。

对于 AITeachMe 这样的教学系统来说，Ingest 越稳定，后面的图谱、对话、出题和画像就越可靠。因此开发时应持续把 Ingest 当成知识闭环的地基，而不是一个附属上传模块。
