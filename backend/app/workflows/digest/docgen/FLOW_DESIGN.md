# DocGen 链路设计

最后更新：2026-04-17

这份文档直接按目标流程写，不解释现在代码。

---

## 1. docgen 的定位

输入：

- 用户上传并解析好的文件内容
- 用户历史对话记录
- planner 已生成并确认的计划大纲

输出：

- 完整的几份知识文档
- 每份知识文档对应的章节内容
- 几份知识文档拼接后的展示内容

一句话：

```text
planner 负责先定大纲
docgen 负责把大纲真正展开成能学的知识文档
```

---

## 2. 当前这条链路想解决什么

用户给了文件，也和系统聊过，也已经有 planner 大纲。

但这时候离真正的知识文档还差很多：

- planner 的章节标题还是粗的
- 每章具体到底讲什么还不够细
- 用户真正想要的文档风格、密度、深度还没有被完整理解
- 每章到底主要依赖哪些文件、哪些段落、哪些外部知识还没定死
- 直接让模型开始写，容易出现章节冲突、重复、缺内容、风格漂移

所以 docgen 需要再做一轮：

```text
大纲增强
-> 用户意图深化
-> 文件摘要
-> 统一确认和分发
-> 逐章生成
-> 逐章增强
-> 合并检查
```

---

## 3. 总体设计原则

### 3.1 速成课 / 系统课先不分章节格式

先统一章节格式，不要一开始就拆两套模板。

现阶段先统一成：

```text
章节导读
-> 概念 / 定义 / 结论
-> 例子 / 例题
-> 关键提醒 / 易错点
-> 本章小结
-> 本章摘要
```

速成课和系统课先只在下面这些地方做差异：

- 内容密度
- 写作语气
- 例题比例
- 解释深度
- 检索偏好

不要先把章节结构搞成两套，不然后面所有节点都会更复杂。

### 3.2 先把“章节要写什么”定细，再开始写

不能 planner 一出大纲就直接生成正文。

必须先补 3 层：

1. 章节大纲增强
2. 用户意图深化
3. 文件材料摘要

然后统一确认，再分发生成。

### 3.3 单章生成要允许继续检索和增强

每章在真正生成正文时，不应该只吃一次 research 结果。

更合理的是：

```text
边生成
-> 边补检索
-> 边补内容
-> 边埋增强标识符
-> 直到该章完成
```

### 3.4 合并后必须再回查

章节单独写完不等于整本文档就好了。

最后必须拿着：

- 章节大纲
- 内容要点
- 生成计划
- 章节摘要

去检查：

- 哪些章节还缺
- 哪些章节冲突
- 哪些章节需要回改

---

## 4. 总时序

推荐总时序：

```text
0. 计划大纲增强
0. 意图识别
0. 文件摘要
1. 确认和分发
2. 章节生成
3. 章节生成增强
4. 合并检查
5. 发布输出
```

依赖关系：

```text
计划大纲增强
意图识别
文件摘要
    -> 确认和分发
    -> 章节生成
    -> 章节生成增强
    -> 合并检查
    -> 发布输出
```

并行关系：

```text
阶段 0 的三个节点可以并行
阶段 2 的章节生成可以按章并行
阶段 3 的章节增强可以按章并行
阶段 4 是全局单点检查
```

为什么这样编排：

1. 先把全局想清楚，再开始写章节
2. 章节真正生成时可以并行，吞吐高
3. 合并检查单独放最后，避免前面阶段互相污染
4. 让章节生成和章节增强分开，便于后续插入更多工具

## 4.1 参考 GPT / Gemini 后，DocGen 还应该补什么

查官方资料后，可以把 GPT Deep Research 和 Gemini Deep Research 的共同点先抽出来：

### GPT / Gemini 共同在做的事情

```text
先给一个 research plan
-> 用户可以改 plan
-> 系统按 plan 去搜、读、推理
-> 运行中展示进度 / thinking / sites browsed
-> 最后输出一份带目录、来源、活动历史的长报告
-> 报告完成后还能继续追问或回补
```

也就是说，它们不是：

```text
给个问题
-> 直接闷头写最终答案
```

而是：

```text
先计划
-> 再执行
-> 执行过程可见
-> 结果可继续迭代
```

### 对 DocGen 的直接启发

DocGen 至少还应该补 5 个能力：

1. **docgen 计划确认点**
   在正式分发章节前，应该先有一份“章节执行计划”，而不是 planner 大纲一来就开始写。

2. **运行中可视化**
   章节生成时要能看到：
   - 当前在写哪一章
   - 这一章主要参考了哪些文件
   - 这一章是否还在继续检索
   - 这一章当前处于“生成 / 增强 / 回改”的哪个阶段

3. **来源可见**
   每章最终不仅要有正文，还应该有：
   - 参考文件
   - 外部来源
   - 哪些内容是本地资料主导，哪些是外部资料补强

4. **生成后可继续追问或回补**
   不是一次 build 完就结束。
   后续应该允许：
   - “把第 3 章再补例题”
   - “把第 2 章讲得更白话”
   - “把最后一章改成总结 + 高频题型”

5. **活动历史**
   至少要能留：
   - 生成计划
   - 执行阶段
   - 章节摘要
   - revision 记录

## 4.2 有哪些地方可以比 GPT / Gemini 更强

如果只做“像 Deep Research 一样先 plan 再写报告”，其实还不够。

你们有一个它们没有的天然优势：

```text
你们不是通用 research 产品
你们是教育文档生成产品
```

所以有 6 个地方是可以做得更强的：

### 1. 更强的本地资料绑定

GPT / Gemini 主要强在 web research。

你们更应该强在：

- 用户上传资料优先
- 章节和文件的绑定更明确
- 每章知道自己主要吃哪个文件、哪个 section

这会让最终文档更像“基于用户资料整理的讲义”，而不是泛化网文报告。

### 2. 更强的章节级生成计划

GPT / Gemini 的 research plan 更像“研究任务计划”。

你们还可以更进一步，做到：

```text
每一章：
讲什么
先讲什么
后讲什么
概念占多少
例题占多少
总结占多少
```

这是教育场景特有价值。

### 3. 更强的例题 / 定义 / 小结分层

通用 deep research 最终产物通常是长报告。

你们更适合做成：

```text
章节导读
概念定义
例题讲解
关键提醒
本章小结
本章摘要
```

也就是让文档天然更适合学，而不是更适合看。

### 4. 更强的章节回改机制

GPT / Gemini 一般是“整份报告完成后继续追问”。

你们更应该支持：

```text
只重写某一章
只增强某一章例题
只补某一章概念解释
只改某一章风格
```

也就是“章节级 revision loop”。

### 5. 更强的教学后处理

你们可以把很多教学增强做成后处理，而不是都压在主生成里：

- 章节摘要
- 术语提取
- 小测题
- 易错点卡片
- 公式推导展开器
- 概念关系图

这会比通用报告产品更像“学习材料”。

### 6. 更强的学后闭环

通用 deep research 一般到报告结束就差不多了。

你们可以继续往后走：

```text
文档
-> 练习
-> profile 更新
-> interact 引用
-> 章节回改
```

也就是真正形成学习闭环。

## 5. planner 需要提供什么

planner 最少要给 docgen 这些内容：

### 5.1 全局信息

```text
subject
user_goal
digest_mode
tone
selected_skillpacks
plan_summary
confirmed_plan_id
planner_session_id
```

### 5.2 计划大纲

至少要有：

```text
chapter_index
chapter_title
chapter_objective
required_elements
search_queries
writing_instructions
source_file_ids
```

### 5.3 最好额外给的 planner 研究结果

最好 planner 再给一份更偏“规划侧”的研究摘要：

```text
planner_grounding
  - summary
  - core_concepts
  - chapter_hints
  - gap_notes
```

这部分不是为了直接写正文，而是为了让 docgen 在一开始就知道：

- 每章大概真正要写什么
- 大纲哪里还虚
- 哪些概念最重要

## 6. 各节点设计

下面每个节点都回答 5 个问题：

1. 干什么
2. 输入
3. 输出
4. 需要什么工具
5. 编排上怎么想

---

## Node 0A. 计划大纲增强

### 干什么

根据 planner 大纲内容，经过检索和 `pri` 聚合，把每个章节的大纲展开细化。

不是重新规划课程。

是把 planner 粗大纲变成“每章具体要写什么”。

### 输入

- planner 计划大纲
- 用户上传文件内容
- 用户历史对话记录

### 输出

- `enhanced_outline`

每章至少输出：

```text
章节标题
章节具体内容要点
章节细化大纲
重点概念
重点定义
重点例题方向
重点提醒
建议检索方向
```

### 需要什么工具

- 本地检索
- 外部检索
- `primary` 模型
  - 用来做聚合和细化

### 编排上怎么想

这一步放在最前面，是因为 planner 大纲太粗，直接拿去分发会产生很多冲突。

必须先把每章具体内容要点定出来。

并行：

- 章节可以并行增强
- 但最后要做一次全局去重和统一

---

## Node 0B. 意图识别

### 干什么

根据：

- 文件
- 对话
- 计划大纲

再做一次更深的用户需求理解。

这里不是简单分类，而是要想清楚：

- 用户真正想要的是怎样一份知识文档
- 每个章节最终应该呈现成什么样
- 内容深度应该是什么样
- 用户到底更想看概念讲解、例题讲解、还是总结式讲义

### 输入

- 用户上传文件内容
- 用户历史对话记录
- planner 计划大纲

### 输出

- `docgen_intent_profile`

至少包含：

```text
用户要的文档风格
用户更关心什么
整体深度
每章希望偏什么
是否偏讲解
是否偏例题
是否偏总结
```

### 需要什么工具

- `primary` 模型

### 编排上怎么想

这一步一定要独立出来。

因为 planner 阶段的意图识别是为了定大纲；
docgen 阶段的意图识别是为了定文档长相。

这两个层次不是一回事。

并行：

- 和“计划大纲增强”“文件摘要”并行

---

## Node 0C. 文件摘要

### 干什么

用 `pri` 模型把每个文件做细致摘要。

目标不是一句话摘要，而是形成文档生成能直接用的“文件级材料画像”。

### 输入

- 用户上传并解析好的文件内容

### 输出

- `file_summaries`

每个文件至少输出：

```text
文件摘要
主要概念
主要定义
主要例题 / 题型
主要结论
适合支撑哪些章节
哪些地方信息密度高
哪些地方更像噪音
```

### 需要什么工具

- `primary` 模型

### 编排上怎么想

这一步必须独立出来，因为：

- 后面确认和分发时需要知道“每章应该主要吃哪些文件”
- 章节生成时也需要知道优先看哪些文件

并行：

- 各文件并行摘要

---

## Node 1. 确认和分发

### 干什么

把前面三份全局结果统一起来：

- 大纲增强结果
- 意图识别结果
- 文件摘要结果

最后生成一份更细致、更统一的章节执行计划，再把各章分发给后续章节生成模块。

### 输入

- `enhanced_outline`
- `docgen_intent_profile`
- `file_summaries`
- planner 原始大纲

### 输出

- `chapter_generation_plan`

每章至少输出：

```text
章节标题
章节大纲
章节内容要点
章节公共生成计划
该章主要依赖哪些文件
该章优先使用哪些 section
该章例题比重
该章解释深度
该章允许后续继续检索的方向
```

还要输出一份全局计划：

```text
全局文档风格
全局章节统一格式
各章之间的边界
避免冲突的统一规则
公共写作规则
公共标识符规范
```

### 需要什么工具

- `primary` 模型
- 可选 `reason`
  - 用来做全局冲突检查

### 编排上怎么想

这一步很关键。

如果没有这一层，前面三个 0 阶段的结果会各说各话：

- 大纲增强想这么写
- 意图识别想那么写
- 文件摘要又支持另一套写法

所以必须先统一确认，再分发。

它本质上是一个全局协调节点。

并行：

- 无
- 必须单点执行，因为它要统一全局

---

## Node 2. 章节生成

### 干什么

根据章节大纲、内容要点、公共生成计划、对应章节材料，深度生成每个章节的正文。

生成过程中允许继续检索和增强，直到该章完成。

### 输入

- `chapter_generation_plan`
- 该章对应的文件摘要
- 该章对应的 section / 原文材料
- 全局公共生成计划

### 输出

- `chapter_drafts`

每章至少输出：

```text
章节正文 markdown
章节内的概念定义部分
章节内的例题部分
章节内的小结部分
后续增强标识符
章节生成摘要
```

### 需要什么工具

- `reason` 模型
  - 用于主生成
- 本地检索
- 外部检索
- web reader
- 内容增强工具

### 编排上怎么想

这是主干节点，必须按章并行。

每章内部推荐时序：

```text
1. 读取该章公共计划
2. 读取该章优先文件和优先 section
3. 生成概念 / 定义
4. 生成例题 / 例子
5. 发现缺内容就继续检索
6. 把需要后续处理的地方埋标识符
7. 生成章节完成稿
```

这里要注意两点：

1. 章节生成过程中允许继续检索
2. 不要指望前面 research 一次性把所有细节都准备好

章节生成内部可以进一步拆成两个子模块：

```text
章节生成：概念、定义
章节生成：例题
```

这两个子模块可以串行，也可以轻并行后再合并。

---

## Node 3. 章节生成增强

### 干什么

根据章节生成时留下的标识符，回头增强原有内容，并统一样式，还要生成章节摘要。

### 输入

- `chapter_drafts`
- 章节中的增强标识符
- 全局公共生成计划

### 输出

- `enhanced_chapter_drafts`
- `chapter_summaries`

每章至少输出：

```text
增强后的章节内容
替换后的图表 / 交互 / 提醒块
统一样式后的章节
章节摘要
```

### 需要什么工具

- `primary` 模型
- Mermaid / image / interactive 生成工具
- markdown 样式检查工具
- 章节摘要生成工具

### 编排上怎么想

这一步必须和“章节生成”分开。

原因：

1. 正文生成和后处理是两件事
2. 章节生成时不应该背太多额外负担
3. 标识符机制可以让后面扩展资产增强更方便

并行：

- 各章并行

---

## Node 4. 合并检查

### 干什么

拿着：

- 章节大纲
- 内容要点
- 生成计划
- 章节摘要

去检查整套文档还有哪些地方需要改。

### 输入

- `chapter_generation_plan`
- `enhanced_chapter_drafts`
- `chapter_summaries`

### 输出

- `merged_markdown`
- `merge_review_report`
- 可选的 `revision_tasks`

至少输出：

```text
整本文档
哪些章节需要改
为什么要改
是否缺内容
是否章节冲突
是否风格漂移
是否大纲和正文不一致
```

### 需要什么工具

- `primary` 模型
- 可选 `reason`
  - 用于全局检查
- markdown merge 工具

### 编排上怎么想

这一步必须是单点全局节点。

因为只有把所有章节放到一起，才能发现：

- 章节重复
- 章节断裂
- 章节标题和内容不一致
- 某章讲太多、某章讲太少

必要时，这一步可以再生成：

```text
revision_tasks
```

把需要修改的章节再丢回章节生成或章节增强节点。

也就是说，这一步可以成为一个轻量回路的入口。

---

## Node 5. 发布输出

### 干什么

把最终结果落盘，并生成前端展示需要的拼接内容。

### 输入

- `merged_markdown`
- `enhanced_chapter_drafts`
- `merge_review_report`

### 输出

- 分章节 markdown
- 合并后的 markdown
- 展示用拼接结果
- manifest

### 需要什么工具

- storage writer
- manifest writer
- markdown merge / split 工具

### 编排上怎么想

发布输出必须最后做。

而且这里要同时保留两种结果：

1. 分章节结果
2. 拼接后的展示结果

因为系统既需要章节级能力，也需要前端一整份展示能力。

---

## 7. 失败策略

必须按“单章失败不拖垮整轮”设计。

### 必须有的降级

1. 文件摘要失败时，至少保留原文件和粗粒度摘要
2. 大纲增强失败时，回退到 planner 原始大纲
3. 意图识别失败时，回退到 planner 意图 + 默认文档风格
4. 单章生成失败时，保留其他章节继续
5. 章节增强失败时，保留章节原稿
6. 合并检查失败时，至少输出已完成章节拼接稿

### 只有这几类情况才整轮失败

- confirmed plan 无效
- 所有章节都生成失败
- 最终发布失败且 staging 也没保住

---

## 8. 最小落地顺序

按这个顺序落最稳：

```text
1. 先补 文件摘要 节点
2. 再补 大纲增强 节点
3. 再补 意图识别 节点
4. 做 确认和分发 节点
5. 章节生成改成吃 chapter_generation_plan
6. 章节增强从章节生成中拆出来
7. 合并检查支持 revision_tasks
8. 最后再补完整的发布结果和 manifest
```

---

## 9. 一句话总结

你想要的 docgen 链路，本质上是：

```text
先把 planner 大纲和用户真正想要的文档长相想清楚
再把文件材料吃透
然后统一确认每章到底该怎么写
再逐章生成
再逐章增强
最后整体验证和回改
再发布
```

这条链路比“直接根据 confirmed plan 一章章写”更重，
但是更符合真正想生成高质量知识文档的目标。
