# DocGen 链路设计

最后更新：2026-04-17

这份文档只写目标流程，不解释当前代码。

---

## 1. DocGen 是做什么的

输入：

- 用户上传并解析好的文件内容
- 用户历史对话记录
- planner 已确认的计划大纲

输出：

- 分章节知识文档
- 拼接后的完整知识文档
- 章节摘要
- 练习与自检内容
- 资产结果与发布结果

一句话：

```text
planner 负责定大纲
docgen 负责把大纲真正展开成完整知识文档
```

---

## 2. 参考 GPT / Gemini 后，这条链路应该怎么理解

从 GPT Deep Research 和 Gemini Deep Research 官方流程里，可以先抽出几个共同点：

```text
先给计划
-> 再执行
-> 执行过程可见
-> 最后产出长结果
-> 结果还能继续迭代
```

对 DocGen 的直接启发是：

1. 不能 planner 一出大纲就直接写正文
2. 正式写之前要先把章节执行计划定细
3. 生成过程中要允许继续检索和补内容
4. 结果出来后要能继续回改，而不是一次性结束

但你们又不只是通用 research 产品，而是教育产品，所以还应该比它们更强：

1. 更强的本地资料绑定
   - 每章明确主要依赖哪些文件、哪些 section

2. 更强的章节级生成计划
   - 每章讲什么
   - 先讲什么
   - 后讲什么
   - 概念/例题/总结占比

3. 更强的教学后处理
   - 章节摘要
   - 术语提取
   - 小测题
   - 易错点卡片
   - 公式推导展开器

4. 更强的章节级回改
   - 只重写某一章
   - 只增强某一章例题
   - 只补某一章概念解释

所以 DocGen 不是“研究完直接写报告”，而应该是：

```text
大纲变细
-> 章节计划确认
-> 逐章生成
-> 逐章增强
-> 全局检查
-> 回改
-> 发布
```

---

## 3. Planner 需要提供什么

DocGen 不重新规划课程，所以 planner 必须先把宏观结构定住。

### 3.1 全局信息

至少要有：

```text
subject
user_goal
digest_mode
tone
selected_skillpacks
plan_summary
confirmed_plan_id
planner_session_id
```

### 3.2 章节大纲

至少要有：

```text
chapter_index
chapter_title
chapter_objective
required_elements
search_queries
writing_instructions
source_file_ids
```

### 3.3 最好额外给的研究结果

最好 planner 再给一份更偏“规划侧”的研究摘要：

```text
planner_grounding
  - summary
  - core_concepts
  - chapter_hints
  - gap_notes
```

这部分不是直接写正文，而是让 DocGen 一开始就知道：

- 每章大概要写什么
- 哪些概念最重要
- 哪些地方可能还虚

## 4. 总时序

推荐总时序：

```text
0A. 计划大纲增强
0B. 意图识别
0C. 文件摘要
1.  确认和分发
2.  章节生成
3.  章节生成增强
4.  合并检查
5.  发布输出
```

依赖关系：

```text
0A 计划大纲增强
0B 意图识别
0C 文件摘要
        -> 1 确认和分发
        -> 2 章节生成
        -> 3 章节生成增强
        -> 4 合并检查
        -> 5 发布输出
```

并行关系：

```text
阶段 0 的三个节点可以并行
阶段 2 的章节生成可以按章并行
阶段 3 的章节增强可以按章并行
阶段 4 是全局单点检查
阶段 5 是最终单点发布
```

### 为什么这样编排

1. 先把全局想清楚，再开始写章节
2. 正文生成和后处理拆开，避免一个节点背太多事
3. 章节按章并行，吞吐高
4. 合并检查放最后，专门处理冲突、重复、缺内容和回改

## 5. 总体设计原则

### 5.1 速成课 / 系统课先不拆成两套章节模板

先统一章节结构，先把链路跑顺。

统一章节格式先定成：

```text
章节导读
-> 概念 / 定义 / 结论
-> 例子 / 例题
-> 关键提醒 / 易错点
-> 本章小结
-> 本章摘要
```

速成课和系统课先只在这些地方做差异：

- 内容密度
- 写作语气
- 例题比例
- 解释深度
- 检索偏好

### 5.2 正文生成前，必须先把“每章到底写什么”定细

不能 planner 一出粗大纲就直接写正文。

必须先补三层：

1. 大纲增强
2. 意图深化
3. 文件摘要

然后统一确认，再正式分发。

### 5.3 单章生成时允许继续检索和补内容

每章不应该只吃一次 research 结果。

更合理的是：

```text
边生成
-> 边补检索
-> 边补内容
-> 边埋后续增强标识符
-> 直到本章完成
```

### 5.4 合并后必须再回查

章节单独写完，不代表整本文档就没问题。

最后必须拿着：

- 章节大纲
- 内容要点
- 生成计划
- 章节摘要

去检查：

- 哪些章节还缺
- 哪些章节冲突
- 哪些章节需要回改

---

## 6. 节点设计

下面每个节点都回答 5 个问题：

1. 干什么
2. 输入
3. 输出
4. 需要什么工具
5. 编排上怎么想

---

## Node 0A. 计划大纲增强

### 干什么

根据 planner 大纲内容，经过检索和聚合，把每个章节展开成更细的大纲和内容要点。

不是重新规划课程。

是把 planner 的粗大纲变成“每章具体要写什么”。

### 输入

- planner 计划大纲
- 用户上传文件内容
- 用户历史对话记录

### 输出

- `enhanced_outline`

每章至少输出：

```text
章节标题
章节内容要点
章节细化大纲
重点概念
重点定义
重点例题方向
重点提醒
建议检索方向
```

### 需要什么工具

- 本地检索
- 外部检索
- `primary` 模型

### 编排上怎么想

这一步放在最前面，因为 planner 大纲太粗，直接拿去分发会冲突很多。

可以按章并行增强，但最后必须做一次全局去重和统一。

---

## Node 0B. 意图识别

### 干什么

根据：

- 文件
- 对话
- 计划大纲

再做一次更深的用户需求理解。

这里不是简单分类，而是要想清楚：

- 用户真正想要的知识文档是什么样
- 每个章节最终应该是什么风格
- 内容深度应该多深
- 用户到底更想看概念讲解、例题讲解还是总结式讲义

### 输入

- 用户上传文件内容
- 用户历史对话记录
- planner 计划大纲

### 输出

- `docgen_intent_profile`

至少包含：

```text
用户要的文档风格
用户更关心什么
整体深度
每章希望偏什么
是否偏讲解
是否偏例题
是否偏总结
```

### 需要什么工具

- `primary` 模型

### 编排上怎么想

这一步必须独立出来。

planner 阶段的意图识别是为了定大纲；
docgen 阶段的意图识别是为了定文档长相。

这两个层次不是一回事。

它和“计划大纲增强”“文件摘要”并行。

---

## Node 0C. 文件摘要

### 干什么

把每个文件做成细致摘要，形成后续生成能直接用的“文件级材料画像”。

目标不是一句话摘要，而是知道：

- 这个文件主要讲什么
- 它更适合支撑哪些章节
- 它哪些段落更有价值

### 输入

- 用户上传并解析好的文件内容

### 输出

- `file_summaries`

每个文件至少输出：

```text
文件摘要
主要概念
主要定义
主要例题 / 题型
主要结论
适合支撑哪些章节
高信息密度段落
噪音段落
```

### 需要什么工具

- `primary` 模型

### 编排上怎么想

这一步必须独立出来，因为：

- 确认和分发时要知道“每章应该主要吃哪些文件”
- 章节生成时也需要知道优先看哪些文件

文件之间可以并行摘要。

---

## Node 1. 确认和分发

### 干什么

把前面三份全局结果统一起来：

- 大纲增强结果
- 意图识别结果
- 文件摘要结果

最后生成一份更细致、更统一的章节执行计划，再把各章分发给后续章节生成模块。

### 输入

- `enhanced_outline`
- `docgen_intent_profile`
- `file_summaries`
- planner 原始大纲

### 输出

- `chapter_generation_plan`

每章至少输出：

```text
章节标题
章节大纲
章节内容要点
该章公共生成计划
该章主要依赖哪些文件
该章优先使用哪些 section
该章例题比重
该章解释深度
该章允许继续检索的方向
```

同时输出一份全局计划：

```text
全局文档风格
全局章节统一格式
各章之间的边界
避免冲突的统一规则
公共写作规则
公共标识符规范
```

### 需要什么工具

- `primary` 模型
- 可选 `reason`
  - 用来做全局冲突检查

### 编排上怎么想

这一步很关键。

如果没有这一层，前面三个 0 阶段的结果会各说各话：

- 大纲增强想这么写
- 意图识别想那么写
- 文件摘要又支持另一套写法

所以必须先统一确认，再分发。

它必须是单点全局节点。

---

## Node 2. 章节生成

### 干什么

根据章节大纲、内容要点、公共生成计划、对应章节材料，深度生成每个章节正文。

生成过程中允许继续检索和增强，直到该章完成。

### 输入

- `chapter_generation_plan`
- 该章对应的文件摘要
- 该章对应的 section / 原文材料
- 全局公共生成计划

### 输出

- `chapter_drafts`

每章至少输出：

```text
章节正文 markdown
概念定义部分
例题部分
本章小结部分
后续增强标识符
章节生成摘要
```

### 需要什么工具

- `reason` 模型
  - 主生成
- 本地检索
- 外部检索
- web reader
- 内容增强工具

### 编排上怎么想

这是主干节点，必须按章并行。

每章内部推荐时序：

```text
1. 读取该章公共计划
2. 读取该章优先文件和优先 section
3. 生成概念 / 定义
4. 生成例题 / 例子
5. 发现缺内容就继续检索
6. 把需要后续处理的地方埋标识符
7. 生成章节完成稿
```

章节生成内部可以进一步拆成两个子模块：

```text
章节生成：概念、定义
章节生成：例题
```

它们可以串行，也可以轻并行后再合并。

---

## Node 3. 章节生成增强

### 干什么

根据章节生成时留下的标识符，回头增强原有内容，并统一样式，还要生成章节摘要。

### 输入

- `chapter_drafts`
- 章节中的增强标识符
- 全局公共生成计划

### 输出

- `enhanced_chapter_drafts`
- `chapter_summaries`

每章至少输出：

```text
增强后的章节内容
替换后的图表 / 交互 / 提醒块
统一样式后的章节
章节摘要
```

### 需要什么工具

- `primary` 模型
- Mermaid / image / interactive 生成工具
- markdown 样式检查工具
- 章节摘要生成工具

### 编排上怎么想

这一步必须和“章节生成”分开。

原因：

1. 正文生成和后处理是两件事
2. 章节生成时不应该背太多额外负担
3. 标识符机制可以让后面扩展资产增强更方便

各章并行。

---

## Node 4. 合并检查

### 干什么

拿着：

- 章节大纲
- 内容要点
- 生成计划
- 章节摘要

去检查整套文档还有哪些地方需要改。

### 输入

- `chapter_generation_plan`
- `enhanced_chapter_drafts`
- `chapter_summaries`

### 输出

- `merged_markdown`
- `merge_review_report`
- 可选 `revision_tasks`

至少输出：

```text
整本文档
哪些章节需要改
为什么要改
是否缺内容
是否章节冲突
是否风格漂移
是否大纲和正文不一致
```

### 需要什么工具

- `primary` 模型
- 可选 `reason`
  - 用于全局检查
- markdown merge 工具

### 编排上怎么想

这一步必须是单点全局节点。

因为只有把所有章节放到一起，才能发现：

- 章节重复
- 章节断裂
- 章节标题和内容不一致
- 某章讲太多、某章讲太少

必要时，这一步可以再生成：

```text
revision_tasks
```

把需要修改的章节再丢回章节生成或章节增强节点。

也就是说，这一步可以成为轻量回路入口。

---

## Node 5. 发布输出

### 干什么

把最终结果落盘，并生成前端展示需要的拼接内容。

### 输入

- `merged_markdown`
- `enhanced_chapter_drafts`
- `merge_review_report`

### 输出

- 分章节 markdown
- 合并后的 markdown
- 展示用拼接结果
- manifest

### 需要什么工具

- storage writer
- manifest writer
- markdown merge / split 工具

### 编排上怎么想

发布输出必须最后做。

而且这里要同时保留两种结果：

1. 分章节结果
2. 拼接后的展示结果

因为系统既需要章节级能力，也需要前端整份展示能力。

---

## 7. 失败策略

必须按“单章失败不拖垮整轮”设计。

### 必须有的降级

1. 文件摘要失败时，至少保留原文件和粗粒度摘要
2. 大纲增强失败时，回退到 planner 原始大纲
3. 意图识别失败时，回退到 planner 意图 + 默认文档风格
4. 单章生成失败时，保留其他章节继续
5. 章节增强失败时，保留章节原稿
6. 合并检查失败时，至少输出已完成章节拼接稿

### 只有这几类情况才整轮失败

- confirmed plan 无效
- 所有章节都生成失败
- 最终发布失败且 staging 也没保住

---

## 8. 最小落地顺序

按这个顺序落最稳：

```text
1. 先补 文件摘要 节点
2. 再补 大纲增强 节点
3. 再补 意图识别 节点
4. 做 确认和分发 节点
5. 章节生成改成吃 chapter_generation_plan
6. 章节增强从章节生成中拆出来
7. 合并检查支持 revision_tasks
8. 最后补完整的发布结果和 manifest
```

---

## 9. 一句话总结

这条链路本质上是：

```text
先把 planner 大纲和用户真正想要的文档长相想清楚
再把文件材料吃透
然后统一确认每章到底该怎么写
再逐章生成
再逐章增强
最后整体验证和回改
再发布
```

它比“直接根据 confirmed plan 一章章写”更重，
但更接近真正高质量知识文档生成。
